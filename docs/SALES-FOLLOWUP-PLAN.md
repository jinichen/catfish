# 销售跟进 (客户档案 + 跟进雷达) —— 阶段 1 计划

10/12 定。用户: **我们自己卖鲶鱼的销售团队**; 客户沟通主要在**个人微信 + 邮件**。
不接 ERP, 只在现有能力上搭。目标是一件事: **跟进不掉线** —— 该回的回了、答应的做了、
久没联系的客户有人提醒。

## 1. 现有积木 (都已在线, 本阶段只复用)

| 早安顾问 | `briefing_advisor.ts`, 现有数据源 = 邮件 50 封 / 日历 / 提醒 | 加客户档案 + 微信两个源, 出跟进卡片 |

## 2. 客户档案 (实体页)

新类型 `customer` (别名「客户」「客户公司」), 一个客户一页:

```markdown
---
type: entity
entity_type: customer
title: <客户公司名>
stage: 线索 | 需求确认 | 已报价 | 商务谈判 | 成交 | 输单 | 暂停
owner: <销售姓名>
contacts: [{name: <联系人>, role: <职务>, wechat: <微信备注名>, email: <邮箱>}]
last_contact: 2026-10-12          # 最近一次双向沟通 (不是我单方面发)
next_action: 周三前发正式报价       # 一句话
next_action_due: 2026-10-15
deal_size: 12万/年                  # 可空, 估算
created: ... / updated: ...
---

## 时间线
- 2026-10-12 · 微信 · 对方问「私有化部署要几台服务器」(未答) [来源]
- 2026-10-10 · 邮件 · 我方发产品介绍 PDF [来源]
- 2026-10-08 · 会议 · 演示, 对方关心数据不出本机 [纪要]
```

- **谁建**: 销售说「把 X 公司建成客户」, 或小鲶在邮件/微信里发现新的潜在客户时**提议**新建 (员工确认才建, 不自动建)。
- **谁更新**: 小鲶处理客户相关的邮件 / 导入微信 / 会议纪要后, 往时间线**追加**一行 + 更新 `last_contact`;
  `stage` / `next_action` 由小鲶**建议**, 员工点确认才改 (阶段是业务判断, 不让模型自己定)。
- **怎么认是哪个客户**: 邮件按发件人域名 / 地址匹配 `contacts.email`; 微信按导出时的群名 / 对方备注名匹配 `contacts.wechat`; 匹配不上的列为「待归属」, 不猜。

### 2.1 销售模板 (不随商品写死)

不同商品的销售阶段和节奏不同 (软件: 线索→报价→谈判; 包装: 询价→打样→报价→试单…)。阶段名、各阶段
多少天没动静算冷、哪个阶段算「已报价」、客户问了多少个工作日没回提醒、报价后几天没回音提醒 —— 全在
「销售模板」里 (`~/.catfish/sales_template.json`, 设置 →「🤝 销售跟进」可改)。没配就用鲶鱼默认模板
(下面 §3 的天数)。小鲶建客户 / 改阶段只认模板里的阶段名。

## 3. 跟进雷达 (早安顾问的新数据源)

每天早上 (和员工手动点刷新时) 扫一遍, 出四类卡片, 每张卡带**依据** (原话 + 来源) 和**一键动作**:

| 规则 | 判据 | 卡片动作 |
|---|---|---|
| ① 客户在等我回 | 客户最后一条消息是问题 / 请求, 之后我方没回复, 超过 1 个工作日 | 起草回复 (按文风) · 标为已处理 |
| ② 我答应的事 | 我方消息里有承诺句 (「明天发」「周三前给」「我确认后回您」), 到期未见对应动作 | 生成提醒 (推到微信) · 起草 |
| ③ 客户冷了 | `last_contact` 超过 N 天 (按阶段: 线索 14 天 / 需求确认与已报价 7 天 / 谈判 3 天) | 起草问候 / 推进消息 · 改阶段为暂停 |
| ④ 报价没回音 | 阶段 = 已报价, 报价后 5 天无客户回复 | 起草跟进 · 提醒 |

- 判据由模型读原话判断 (承诺句、问题句), 但**卡片必须引用原话**, 员工一眼能核对; 判不准的宁可不出。
- 关掉的卡片走现有「关闭账本」, 不会第二天又冒出来。
- 天数阈值做成设置, 不写死。

## 4. 微信这条腿的限制 (要先说清楚)

1. **只能事后读**: 数据来自员工「合并转发」导出的 ZIP, 没有实时同步。雷达在微信上的新鲜度 = 最近一次导入。
   - 建议的工作习惯: 跟客户聊完或每天下班前, 把客户聊天合并转发一次拖进小鲶。
   - 待验证: 销售能否把客户聊天**直接合并转发给微信里的小鲶机器人** (iLink 是否把合并转发消息完整交给 hermes)。可行的话就不用拖 ZIP。
2. **小鲶不在个人微信里替销售发消息**: 个人微信自动化有封号风险。小鲶只起草, 销售复制发送。
3. 邮件这条腿是实时的 (现有邮件读取), 不受上面限制。

## 5. 数据边界

- 客户档案、时间线、雷达结果**全部在销售本机** (`~/.catfish/`), 中央端不存。
- 起草和判据走模型时, 只有相关片段经网关 (网关不落盘), 跟现在聊天一致。
- 阶段 3 才有「主管看全组漏斗」: 由销售**主动发布**结构化摘要 (阶段 / 金额 / 下一步, 不含聊天原文) 到部门 wiki-hub, 沿用现有「员工主动 push」例外。

## 6.1 实现备注 (10/12 落地时的取舍)

- **一个工具**: `catfish_customer` (action = upsert / log / done / get / list / radar / template)。核心工具每个都占
  gateway tool cap, 合成一个只占一格 (DEFAULT_MAX_TOOLS 44→45), 同步进 hermes `_PROMOTE` + gateway `ALWAYS_ON`。
- **雷达是确定性规则**: "是不是问题 / 承诺"由模型在 log 时判 (kind 字段), 雷达只按时间线和模板算,
  同样的档案永远出同样的卡; 卡片 uid 稳定, 关卡复用早安关闭账本。
- **待归属**: 第一版不单独存「待归属」列表 —— 认不出客户时工具直接报错 + 给候选, 由小鲶问员工; 不会记错客户。
- 早安「客户跟进」是独立一条 (`CustomerFollowupStrip`), 没有客户档案时不显示, 不改原有早安两栏布局。

## 7. 验收

1. 建 3 个虚构客户, 导入一段虚构微信 + 几封虚构邮件 → 时间线自动出现对应条目, 来源可点。
2. 构造四类情形各一 → 早安出四张卡, 每张引用原话; 关掉后第二天不再出现。
3. 「我答应的事」生成的提醒到点推到微信 (Windows)。
4. 改阶段必须经员工确认; 匹配不上的消息进「待归属」, 不被塞进错的客户。
