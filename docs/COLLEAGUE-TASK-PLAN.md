# 请同事帮忙 · 派任务给多位同事 —— 计划

11/4 鸿波定。原来的「请同事的小鲶帮忙」(P50, 9/10) 只能找**一个人**、对方要在 **10 分钟**内点同意,
之后**发起人这台电脑一直开着、在局域网里直连对方的小鲶**派工等结果。关机、合盖、不在一个网段就断。
四类任务 (立即 / 定时 / 周期 / 多阶段) 都要「发出去就不用管, 到点对方自己做, 结果自己回来」,
所以改成**异步任务单**, 跟「一起填表」走同一个邮筒。

## 0. 统一模型

发起人写一张任务单 → 发给多位同事 → 每人各自决定接不接 → 接下后在**他自己的电脑上**由他的小鲶
(或他本人) 做 → 他核对后点「交回」→ 结果经中央转交, 只回到发起人电脑。

- 中央只转交 (不透明 payload, 不解析、不记日志、取走即清空), 跟填表同一套 (`room_link_mailbox`)。
- 对方同意时看到的只有: **要做什么、什么时候 (截止)、结果交给谁**。不列工具 (11/4 鸿波: 员工看不懂, 把关在执行时)。
- 执行时的把关照旧: 只读的不用批; 发邮件 / 发消息 / 删东西每次问对方本人; 结果对方点「交回」才发出。
- 这是「请」不是「命令」: 拒绝是正常结果, 界面上显示原因。

## 1. 第一步 (11/4 做完): 立即完成的任务 · 多人 · 截止 · 汇总

| 位置 | 内容 |
|---|---|
| 中央 `room_link_db.py` | 加 `TASK_KINDS`: task_invite / task_reply / task_remind / task_cancel, 期限规则同填表 (截止后 7 天, 夹在 [10 分钟, 30 天]) |
| tool-bridge `colleague_tasks.py` | 本机账本 `~/.catfish/collab_tasks/` + 收发 + 状态; `pim/ctask_*` 给界面; `forms_net.py` 投 / 取通用化 |
| 小鲶工具 | 合进 `catfish_form` 的 `task_*` action (网关工具数已到 49 上限, 不新增工具): 派出 / 催 / 取消要员工确认; 做同事派来的任务只能 `task_draft` 存结果草稿, **没有接下 / 交回 / 不接** |
| Companion | `commands/colleague_tasks.rs` 只放行 `pim/ctask_*`; 「协同」页左上换成 `TasksPanel` (同事请我做的 / 我请同事做的), 弹层 `TaskComposer` / `TaskWork` / `TaskProgress`; 20 秒取一次邮筒, 新任务 / 被催 / 取消 / 交回 / 不接发系统通知, 待处理 + 在做算红点 |

信封 (中央看不懂也不看):

```
task_invite  {v, task_id, task: {title, text, deadline}}      不含别的收件人, 不含别人的结果
task_reply   {v, task_id, status: accepted|done|declined, result?, reason?, at}
task_remind  {v, task_id, text?}
task_cancel  {v, task_id}
```

规则:

- 一次最多 20 人; 任务说明 ≤ 2000 字; 交回的结果 ≤ 15000 字 (邮筒单封 64KB)。附件这一步不做, 长材料用邮件。
- 截止可以只给日期 (当天 23:59 截止) 或带时分 (`2026-11-05T18:00`, 本机时间); 不给 = 不限时。
- 发起人看到的状态: 未发 / 等回应 / 在做 / 已完成 / 逾期完成 / 不接 / 超时未回 / 超时未交 / 已取消。
- 收件人: 待处理 / 在做 / 已交回 / 不接 / 已取消。交回后可以改了再交 (后交的覆盖); 回了不接还能再接下。
- 催只催还没交回的; 取消只通知还没交回的, 已交回的结果留着。
- 防冒名: 同编号别人发的任务单不覆盖; 不是这个任务收件人发来的回复不收; 催 / 取消只认原发起人。
- 「让小鲶做」走工作台一次性请求 (跟填表的「让小鲶先填」同一条路), 同事原话放在 `<<< >>>` 里当任务内容,
  提示词写明对外操作先问、结果只存草稿、不要自己发给对方。
- 老版 Companion (< 1.2.56) 取件不带 task_* kind, 任务单留在中央等它升级 (不会被取走丢掉); 发起人那边一直是「等回应」, 进度页提示对方升级。
- 老中央 (不认 task_*) 投 / 取都回 400: 界面说「中央端版本太旧, 请管理员升级」。
- 原来的在线直连 (P50) 发起入口去掉; 右栏「等我点头」照旧, 接老版本同事发来的在线请求和工具审批。

## 2. 第二步 (11/4 做完): 定时 / 周期

任务单多一个 `schedule` (空 = 马上做):

```
{"kind": "once", "at": "2026-11-05T09:00"}                                 定时做一次 (最远一年)
{"kind": "cron", "expr": "0 9 * * 1", "until": "2026-12-31", "times": 8}   周期; until / times 至少一个 (最长一年, 最多 100 次)
```

| 位置 | 内容 |
|---|---|
| tool-bridge `colleague_tasks_schedule.py` | 校验 / 中文说明 / 建删 hermes 定时任务 (`cron.jobs.create_job`, 跟 `hermes cron create` 同入口) / 晚了多久 / 结束没 |
| tool-bridge `colleague_tasks_periodic.py` | 收件人这边: 接下建定时、每期结果、核对交回、退出、对方改了、同步时补跑和收尾 |
| `colleague_tasks.py` | 任务单带 schedule 和 rev; 发起人「修改任务」(rev+1 重新发, 对方要重新同意); 每期回复 `status=period` |
| 小鲶工具 | `catfish_form` 加 `task_period` (定时 / 周期任务的这一次结果) 和 `task_create` 的 schedule 参数 |
| Companion | 派任务时选「马上 / 定时做一次 / 周期做」(`TaskSchedulePicker`); 收件人 `TaskWorkScheduled`; 发起人进度按期列结果、「修改任务」 |

流程:

- 同事接下 = 在**他电脑上**建定时任务 (名字「同事任务·…」, 设置里的定时任务列表也看得到); 可勾「每次做完直接交回, 不用我看」,
  默认每次他核对后点「交回」。
- 到点小鲶无人值守做一次, 用 `task_period` 存结果。提示词写明: 不发邮件 / 消息 / 派任务 / 删东西, 需要的写进结果等他回来处理。
- **无人值守时要审批的步骤**: hermes 现在是 `approvals.cron_mode=deny` —— 不执行, 小鲶在结果里写明哪步没做
  (不是原先设想的「停在等我点头、回来点了接着做」; 那要改 hermes 定时执行的中途挂起, 这一步没做)。所以默认每次核对后交回。
- **错过了**: 周期任务 hermes 开机后补跑一次 (不连发); 一次性任务 hermes 过点 2 分钟就直接丢掉 (11/4 实测), 由同步补建一个
  1 分钟后的, 只补一次; 还没做成就通知同事「没做成」, 他可以点「现在让小鲶做一次」。结果按应跑时间标「晚了多久」
  (同一个周期里手动多做的一次不算晚)。
- **结束**: 做满次数 / 过了结束日自动删定时任务, 两边都显示「已结束」。
- **双方都能停**: 发起人「取消任务」(对方本机定时删掉) 或「修改任务」(对方定时先停, 重新同意后按新的建); 同事「退出」(写原因)。
- 同事在定时任务列表里手动删了它: 显示「定时没了」, 可以「重新安排」或退出。
- 发起人进度: 等回应 / 已安排 / 进行中 / 已完成 (一次性) / 已结束 / 不接 / 已退出 / 等重新同意 / 已取消; 每人每次的结果按次列出,
  「让小鲶汇总」读得到每期结果。
- 收件人状态: 待处理 / 已安排 / 进行中 / 待核对 / 已结束 / 没做成 / 定时没了 / 要重新同意 / 不接 / 已退出 / 已取消;
  要他动手的 (待处理 / 待核对 / 要重新同意 / 没做成 / 定时没了) 算红点, 小鲶做完一次等核对会发系统通知。
- 中央不用改: 每期结果也是 `task_reply`, 邮筒规则同第一步。

## 3. 第三步 (11/4 做完): 多阶段

| 位置 | 内容 |
|---|---|
| tool-bridge `colleague_tasks_pipeline.py` | 流程账本 `~/.catfish/collab_tasks/pipelines/`; 建流程 / 放行到下一段 / 完成 / 取消; 同步时「这一段都回了」提醒 |
| `colleague_tasks.py` | 任务带 `context` (发起人放行的上一段结果, ≤ 15000 字) 和 `pipeline_id`; 「请他重做」(`redo`, 只给一个人发 rev+1 + 要求) |
| Companion | 「协同」页「多阶段」按钮 → `PipelineComposer` (一段一段写做什么 + 谁来做); `PipelineProgress` (各段状态、交接内容、放行); 任务进度里「请他重做 / 再请他一次」 |

- 一个流程 2–8 段, 按顺序; 一段可以派给几个人 = 并行。**每一段就是一个普通的马上做任务**, 同事那边照常接下 / 交回。
- **发起人电脑来协调, 中央不存任何一段的内容**: 这一段的结果先回到发起人; 「交给下一段的内容」默认是这一段每人交回的结果
  (标明是谁), 发起人删改后点「放行到下一段」才发给下一段的人 —— 下一段只看得到放行的那段话。
- 这一段都回了 (交回 / 不接) 发通知、算红点; 还有人没交也可以放行 (不等了), 没交的人收到取消。最后一段放行 = 完成流程。
- 某一段出问题只动那一段: 加人、「请他重做」(写要怎么改; 他上次交的当草稿留着, 在上面改)。
- 「让小鲶汇总各段」: 逐段读 `task_results`, 全在本机。
- 小鲶这一步不能自己建流程 (工具说明字数已到上限); 跟它说要做多阶段, 让员工在「协同」页建。
- 没接进 `catfish_workflow`: 工作流是一口气跑完的固定步骤, 「等同事几天」放进去会让一次运行挂好几天;
  多阶段单独做成流程, 需要的话以后让工作流的一步「发起一个多阶段任务」。
- 同事要 Companion 1.2.58 以上才看得到「上一段结果」(老版本只看到任务说明)。

## 4. 不做 (第一步)

- 附件、图片。
- 中央 web 上看任务内容 (那就等于内容落中央)。
- 「主管强制指派」: 主管派给下属也由对方本人同意。
- 端到端加密: 跟填表一样靠「不透明 + 取走即清空 + 不记日志」, 客户要求时再加。
