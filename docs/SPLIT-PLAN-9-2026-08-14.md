# 9 个文件的拆分方案 (2026-08-14 夜)

## 为什么是这 9 个

`scripts/check_file_sizes.sh` 报 34 个必拆。按**真正影响拆分风险**的两个轴分：

| 类型 | 个数 | 有测试 | 编译器兜得住 |
|---|---:|---:|---|
| `.py` | 13 | 7 | 否 |
| `.rs` | 9 | 8 | 是 |
| `.tsx` | 5 | 0 | 是 |
| `.ts` | 4 | 1 | 是 |
| `.js`/`.sh` | 3 | 0 | 否 |

这 9 个是**类型检查 + 测试双保险**的那一批。文件大小不是主轴 —— 8/14 拆
`embedding.rs`(890 行) 之所以安全，靠的是自然边界 + `cargo check` 立刻兜底 +
拆完有测试能跑，跟"小"没关系。

对照：`app.py` 3779 行是最该拆的，也是最危险的（无类型检查、无测试文件、
全员主链路）。它不该顺手拆，**拆之前先补测试**。

---

## 通用规矩

1. **一次一个文件**，拆完立刻 `cargo check` / `npm run build`，绿了才动下一个。
2. **纯搬迁，不改逻辑**。搬迁和改逻辑混在一起，review 时分不出哪个动作引入了问题。
3. 搬完**跑一遍该模块的测试**（Rust 内联测试会跟着代码走，注意别落下）。
4. 提交信息里写清**切在哪条边界、为什么是这条**。

> 8/14 记的一笔：某天 4 个 bug 里 3 个来自重构。所以宁可慢。

---

## 逐个的边界

### 1. `commands/skills.rs` (1086) — 最适合第一个

结构非常整齐，三段几乎不交叉：

```
 35-460   数据类型 + 解析 + 扫描 + 列举      → skills_list.rs
496-935   安装 / 卸载 / zip 导入 / 恢复      → skills_install.rs
938-1030  MCP server 增删                    → skills_mcp.rs
460-495
1030+     #[tauri::command] 薄封装           → 留在 skills.rs
```

`skills.rs` 只剩 command 层（每个就几行，转调 `*_blocking`），职责一眼看得清。

共用的 `home_dir()` / `augmented_path()` 放 `skills_list.rs` 里 `pub(crate)`，
或者更干净：挪进已有的 `util::paths`。

### 2. `commands/wiki_write.rs` (805)

```
 18-131   slug 校验 / 归一化 / 碰撞检测      → wiki_slug.rs
393-560   删除 + 影响面计算                  → wiki_delete.rs
其余      create / update / uninstall / ingest → 留在 wiki_write.rs
684-726   日期工具 (chrono_today/days_to_ymd) → 挪进 util (它跟 wiki 无关)
```

那两个日期函数尤其该搬 —— 手写的儒略日转换躺在 wiki 写入文件里，
放在这儿只是历史。

### 3. `services/phishing_scan.rs` (870，其中 273 行是测试)

五个 `scan_*` 函数结构一致、互不依赖：

```
116-209   工具函数 (parse_sender / extract_urls / url_host / homograph / ext)
212-310   scan_sender
311-385   scan_urgent_keywords
386-486   scan_links
487-581   scan_attachments
582-...   scan_content
```

切法：`phishing_rules.rs`（工具 + 5 个 scan）+ `phishing_scan.rs`（编排 + 类型 + 测试）。
测试跟着被测函数走。

### 4. `commands/codex_backend.rs` (1057)

```
244-330   路径 / 候选 / 版本解析 / 探测      → codex_probe.rs
470-528   shim 安装卸载 (含 cfg 分支)        → codex_shim.rs
605-722   hermes_api_ready / 网关进程 / 重启 → codex_gateway.rs
其余      build_status + command 层          → 留下
```

搬的时候别把它落下，那是一条真踩过的坑。

### 5. `commands/hermes_install.rs` (1533，其中 197 行是测试)

最大的一个，但结构分明：

```
330-460   原子写盘 / 事务 / 完成标记         → hermes_install_txn.rs
414-530   版本解析 / 健康检查 / 可执行探测   → hermes_install_health.rs
542-670   中断事务恢复 / 锁                  → hermes_install_recover.rs
其余      安装流程编排 + 进度上报            → 留下
```

事务那组（写盘 + 标记 + 恢复）是最独立的一块，也最该有自己的文件 ——
"装到一半断电"的正确性全在那里。

### 6. `services/email_scheduler.rs` (1049，其中 146 行是测试)

```
 67-158   状态文件读写 / 持久化              → email_state.rs
518-562   phishing / political 扫描集成      → email_scan_hooks.rs
其余      调度循环 + 评级 + command          → 留下
```

⚠ 858 行那个 client 我 8/14 刚改成走 `trust_central`，搬的时候注意别退回裸的。

### 7. `lib/chat.ts` (907) — ⚠ 跟其它八个不是一类

它不是"一个文件塞了多件事"，是**一个函数太大**：

```
179-903   streamChat()   ← 725 行，占全文件 80%
```

拆文件解决不了 —— 把一个 725 行的函数搬到另一个文件，那个文件还是 725 行。
真正要做的是**分解这个函数**（SSE 解析 / 工具调用循环 / 中断处理 / 错误分类），
那是改逻辑不是搬迁，风险等级完全不同。

建议：**这个单独排一次**，而且先补测试。现在 `chat.test.ts` 有 11 条，
覆盖的是 `computeIdleTimeoutMs` 和外围，不是 `streamChat` 本体。

### 8. `services/autostart.rs` (883，其中 173 行是测试) — ⚠ 启动路径

```
 93-275   依赖自检 (jieba / playwright / agent-browser)  → autostart_deps.rs
276-670   hermes config.yaml 的 MCP 段落自动修补          → autostart_mcp_patch.rs
671-1046  各个进程的起停 (tool-bridge / local-search / chrome)
```

第二段（`patch_hermes_config`）自带测试，最独立，可以先只搬它。

**断了的后果是 Companion 起不来**，所以：搬完不只 `cargo check`，
要真起一次看那几行 `autostart: xxx started`。

### 9. `services/oauth.rs` (990，其中 53 行是测试) — ⚠ 认证

```
736-870   回调解析 / authorize URL 拼装 / urlencode / 随机串  → oauth_url.rs
848-863   id_token 解码                                        → oauth_token.rs
919-1000  keyring 存取                                         → oauth_store.rs
其余      登录流程 / 刷新 / 会话                                → 留下
```

⚠ **断了是全员登不上**。而且这里有条红线：密码/密钥只走 OS 凭据库，
不进配置文件、不进日志。搬 keyring 那段时逐行看，别顺手加日志。

建议放最后，而且搬完要真走一遍登录 + 刷新。
