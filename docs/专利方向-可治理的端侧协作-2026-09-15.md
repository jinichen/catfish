## 0. 三个方向共用的一个原语

catfish 的公理是"中央端严禁看到员工端的数据"，但产品又要"中央可治理"（限流、
撤销、审计、合规）。现在的代码是把这对矛盾**绕开**：内容不经过中央（P50 邮筒只传
握手，任务直连对端 hermes；早安分析在本机 hermes 跑；审计链在本机）。绕开的代价
是功能封顶：跨网段不能协同、委托只能一跳、审计要么全给要么不给。

三个方向解的都是同一件事，用的也是同一个原语：

**端侧对内容做签名承诺（commitment），中央只存承诺不存内容，治理动作作用在承诺上，
事后端侧出示内容即可对照承诺验证。**

- 承诺 = `H(内容)` + 端侧密钥对它的签名 + 元数据（谁、给谁、何时、什么类型、多大）
- 中央拿承诺做：限流、撤销、去重/防重放、审计留痕、完整性锚定
- 中央永远拿不到内容；但任何一方事后拿内容出来，都能跟中央留的承诺对上

这个原语要求每台员工机器有一对**非对称密钥**。现在没有——`install_id` 只是 32 位
十六进制随机串，hermes 的 room grant 用的是 HMAC（`hosted_room_peer.py`
`issue_room_grant`），只有签发方自己能验。所以三个方向的第一步是共同的：给每台
安装生成 Ed25519 密钥对（私钥留本机 `~/.catfish/`，公钥连同 `install_id` 登记到
中央 identity），中央变成一个**只存公钥的目录**。这一步本身没有专利性，但它是下面
一切的地基。

## 1. 可治理的盲中继（Governed Blind Relay）

### 1.1 技术问题

两名员工的本地 agent 协作时，A 要把任务派给 B 的 hermes 并拿回结果。任务内容
（prompt、中间输出、最终回复）属于员工数据，中央不能看；但企业又要求中央能限流
（防一个人把全公司的 agent 当算力用）、能撤销（B 反悔或离职时立即切断）、能审计
（谁在何时向谁派了多少活、成没成）、能防重放。

### 1.2 现状与不够之处

P50 现在的实现（`roomLinkHandshake.ts` / `room_link_router.py`）：

- 握手（request / grant）经中央邮筒，载荷 ≤ 64 KB，取走即清空，10 分钟 TTL，只留
  from/to/kind/时间戳。这一段中央确实看不到内容（载荷不解析）。
- 任务本体走 **A 直连 B 的 hermes 8642**（`dispatchToPeer` →
  `${grant.target_url}/v1/runs`），中央完全不参与。

不够之处有两个层面：

1. **功能**：直连要求 A 能路由到 B 的内网 IP，跨网段、在家、VPN 分段全部失效。
   前面分析过，两台可以靠"都在办公室"绕过去，十台绕不过去。
2. **治理**：因为中央不参与任务本体，中央对"派了什么、派了多少、还在不在跑"一无
   所知；限流做不了，撤销只能靠 B 本机 hermes 检查 grant（A 可以在 grant 有效期
   内一直派）；审计只有握手那一条。

一个朴素的解法是让中央做 TLS 反代中转任务流量——但那样中央就看到内容了，违反
公理。另一个朴素解法是端到端加密后经中央中转——中央看不到了，但也治理不了了：
它不知道一条密文是派工还是状态查询、不知道是不是重放、B 撤销时它不知道该断哪条。
**难点是既盲又能治理**，这就是方案要解的。

### 1.3 技术手段

**信道**：A、B 各自向中央发起**出站**长连接（WebSocket；退化为长轮询也行），中央
按 `session_id` 把两端配对转发。因为两端都是出站，NAT/网段无关。

**会话建立**（复用现有邮筒握手，加两样东西）：

1. A 的 request 里带 A 的临时 X25519 公钥；B 的 grant 回信里带 B 的临时公钥。
   两端各自派生会话密钥（X25519 → HKDF），之后所有中继消息用 AEAD
   （ChaCha20-Poly1305）加密。密钥协商本身经过邮筒——邮筒是中央，但它只能看到
   公钥，算不出会话密钥。
2. B 向中央**登记会话策略**（B 用自己的 OIDC 身份调 `/api/room-link/relay/open`）：
   `{session_id, peer: A, allowed_kinds: [dispatch, status], max_messages, max_bytes,
   expires_at, grant_digest}`，并用 B 的安装私钥签名。这份策略是**资源方 B 声明、
   中央执行**的——中央不需要理解内容就能知道"这条会话只许派工和查状态、最多 N 条、
   到点失效"。

**中继消息格式**（每条）：

```
envelope (明文, 中央可见):
  session_id, seq, from, to, kind, size, ts,
  content_hash = SHA256(plaintext),
  sig = Sign_sender(session_id | seq | kind | content_hash | ts)
body (密文, 中央不可见):
  AEAD(session_key, plaintext, aad = envelope)
```

`kind` 在信封里是明文——但 kind 只是"派工 / 状态 / 结果 / 审批请求"这种类型，
不是内容。把 kind 放明文正是让中央能执行 `allowed_kinds` 的关键。

**中央对每条消息做的事**（全部只依赖信封）：

- 校验 `sig` 用的公钥来自目录（发送方的安装公钥）→ 中央无法伪造消息
- `seq` 必须严格递增且未见过 → 防重放（中央这一层）；接收方再验一次 → 防中央重放
- `kind ∈ allowed_kinds`、累计条数/字节 ≤ 策略 → 限流与能力边界
- `expires_at` 未到、会话未被撤销 → 否则拒绝并通知对端
- 存信封（不存 body；body 转发后即丢，或最多短存到对端 ACK）→ 审计留痕

**撤销**：B 的 Companion 调 `/api/room-link/relay/revoke {session_id}`（B 的 OIDC
身份），中央标记会话失效、断开转发、给 A 推一条 `revoked`；同时 B 本机 hermes 也
撤 grant（现有机制）。两道门：中央这道让"A 继续往 B 塞"在到达 B 之前就被拦住，
B 本机那道让"绕过中央直连"也进不来。

**事后可验证**：争议时（"B 说 A 派了不该派的活"），A 或 B 出示明文，审计员用
中央留存的信封验证 `SHA256(明文) == content_hash` 且签名有效。中央从未见过明文，
但能证明"这条内容就是当时那条，是谁发的，什么时候"。反过来，中央或任何第三方
**无法**从信封反推内容（哈希单向）。

### 1.4 为什么中央看不到却能治理

把"治理需要的信息"和"业务内容"拆开：治理需要的是**类型、数量、方向、时序、
归属、真伪**——这些全在信封里，是明文；业务内容在 body 里，是密文。信封的每个
字段都由发送方签名，中央改不了；body 的 AEAD 用信封做 AAD，信封和 body 绑死，
中央换不了。策略由资源方 B 声明并签名，中央只是执行者。

### 1.5 攻击与失效场景

| 场景 | 应对 |
|---|---|
| 中央被攻破，运营方想看内容 | 只有密文 + 哈希，看不了 |
| 中央丢消息 | A 的 seq 断档 / 超时，A 侧显示失败；不会静默 |
| 中央重放旧消息给 B | B 侧 seq 校验拒绝 |
| 中央篡改 kind 逃避 allowed_kinds | kind 在签名覆盖范围内，B 验签失败 |
| A 在 grant 内狂派 | 中央按 max_messages/max_bytes 拦；B 本机 hermes 的 grant 仍是最后一道 |
| A 直连 B 绕过中央 | B 的 hermes 8642 仍受 API_SERVER_KEY + grant 守门，直连本来就允许（同内网）；策略上可让 B 的 grant 里带 `relay_only` 标志，hermes 侧拒绝非中继来源（需要 plugin patch） |
| B 撤销后 A 的进行中任务 | 中央断转发 + B hermes 拒后续调用；已在 B 机器上跑的那一次由 B 本人在 P49 审批面板里停 |
| 会话密钥泄露 | 每会话临时密钥，只影响该会话；前向保密 |
| 信封里的 size/ts 泄露业务信息 | 承认这是元数据泄露，跟邮筒现在留 from/to/时间戳是同一级别；可加 padding 到固定桶 |

### 1.6 实现落点

- **central gateway**：新 router `room_link_relay_router.py`（WS `/api/room-link/relay`
  + REST open/revoke），PG 表 `relay_sessions`（策略）、`relay_envelopes`（审计，
  只有信封）。复用现有 `get_current_user` 做 OIDC 鉴权。多 worker 下 WS 配对要
  走 Redis pub/sub 或让同一会话固定到一个 worker（先单 worker）。
- **identity**：`install_id` 登记表加 `public_key` 字段 + `/registry/installs` 查询。
- **Companion Rust**：安装密钥对生成/存储（`~/.catfish/install_key`，chmod 600）；
  WS 客户端；X25519 + HKDF + ChaCha20-Poly1305（`ring` 或 `libsodium`）；
  信封签名/验签。
- **Companion TS**：`roomLinkStore.dispatch` 加一条分支——直连失败（或策略要求）
  时走中继；B 侧收到中继 dispatch 后转发到本机 hermes 8642（loopback），hermes
  不感知中继存在。
- **hermes**：零改动（`relay_only` 标志是可选增强，需要 plugin patch）。

工作量：MVP 2–3 周（单 worker、无 padding、无 relay_only）。

### 1.7 权利要求的核心

独立权利要求（方法）大意：一种中央服务器不可见内容的 agent 间任务中继方法——
资源方向中央登记**签名的会话策略**（允许的消息类型、配额、有效期）；发送方对
每条消息生成含类型、序号、内容哈希的**签名信封**并以信封为关联数据加密内容；
中央**仅依据信封**执行策略校验、序号防重放、配额限制并留存信封；接收方验证签名
与序号后解密；资源方可随时撤销使中央停止转发；争议时任一方出示内容与留存信封
比对验证。

从属权利要求：kind 明文化以实现类型级策略；策略与能力 grant 绑定（grant_digest）；
双道撤销；size padding；多 worker 下会话亲和。

### 1.8 在先技术与区分点

- **Signal / MLS / 端到端加密消息**：解决的是隐私，中继不执行任何业务策略，也不留
  可验证承诺。区分点：中央按资源方声明的策略对密文流量做类型级治理。
- **TLS 终结反代 / API 网关**：能治理但看得到内容。区分点：不可见。
- **Tor / mixnet**：中继盲，但没有资源方策略、没有承诺链、没有撤销。
- **Certificate Transparency 式承诺日志**：只留痕不转发。区分点：转发与留痕合一，
  且策略执行前置。
- **OAuth 资源服务器按 scope 限制**：scope 在 token 里，资源服务器看得到请求内容。
  区分点：策略执行者（中央）看不到内容。

风险评估：中。单个元素都有在先技术，可授权性押在"资源方签名策略 + 信封级治理 +
承诺留痕 + 内容不可见"这个组合上。这是三个方向里工程价值最直接的一个——不做它
多机协同就只能同内网用。

## 2. 多跳能力委托（Attenuating Multi-hop Delegation）

### 2.1 技术问题

A 请 B 的 agent 干一件事，B 的 agent 干到一半发现需要 C 的能力（C 的文件、C 的
agent 跑一段）。现在只能 B 的 agent 停下来，B 本人另起一个对 C 的请求。这时：
C 看到的是"B 要"，不知道根因是 A 的任务；A 不知道自己的任务扩散到了 C；A 撤回
对 B 的授权时 B→C 那条还在跑；审计上 A→B 和 B→C 是两条互不相关的记录。

企业要的是：委托可以链式进行，但**每一跳权限只能收窄不能放大**、**每一跳本人可拒**、
**发起方能限制扩散深度**、**任一跳撤销全链下游失效**、**审计能还原完整委托链**——
且中央仍然看不到任务内容。

### 2.2 现状与不够之处

hermes 的 room grant（`hosted_room_peer.py`）是 B 的 hermes 用 HMAC 签给 A 的，
字段有 `room_id / permissions / expires_at / target_install_id` 等 13 项，P49 patch
把 permissions 限到 `(dispatch, status)`。它是**一跳**的：

- HMAC 只有签发方能验，C 的 hermes 无法验证"B 持有的那张 A→B grant 是真的"，
  所以链接不起来。
- grant 里没有 parent、没有 root task、没有 depth。
- 撤销是签发方本地的事，不会传播。

### 2.3 技术手段

在 hermes grant **之外**加一层 catfish 的**委托证书**（delegation certificate），
hermes grant 继续负责 `/v1/runs` 的实际鉴权，委托证书负责"C 的 Companion 该不该
同意签发 hermes grant"。这样不动 hermes 上游。

**委托证书**（每跳一张，由本跳的资源方用安装私钥签名）：

```
cert_i:
  root_task_digest      # A 的原始任务 (prompt_digest, 已有) —— 全链相同
  originator            # A 的 install_id —— 全链相同
  max_depth             # A 在发起时声明；0 = 不许转委托
  depth                 # 本跳深度 (A→B = 1, B→C = 2)
  parent_cert_digest    # 上一跳证书的哈希；第一跳为 null
  issuer / subject      # 本跳资源方 / 本跳被授权方
  permissions           # ⊆ parent.permissions
  capability_scope      # ⊆ parent.capability_scope (能力目录子集, capability_digest 已有)
  expires_at            # ≤ parent.expires_at
  reason                # 本跳申请理由 (明文给 C 本人看; 不上中央)
  sig_issuer
```

**签发规则**（C 的 Companion 在同意前机械检查，本人再决定）：

1. 链完整：从 cert_i 沿 `parent_cert_digest` 回溯到第一跳，每张签名有效（公钥从
   中央目录取），`root_task_digest / originator` 全链一致。
2. 单调收窄：`permissions_i ⊆ permissions_{i-1}`、`scope_i ⊆ scope_{i-1}`、
   `expires_i ≤ expires_{i-1}`、`depth_i = depth_{i-1} + 1 ≤ max_depth`。
3. 不成环：链上 install_id 不重复。
4. 中央撤销集里没有链上任何一张证书的哈希。

四条都过，才把请求呈给 C 本人，并**把整条链展示给 C**（"A 让 B 做 X，B 因此
需要你的 Y"），C 可拒。C 同意后：C 的 hermes 签 hermes grant 给 B 的 agent，
C 的 Companion 签 cert_2，两者一起回给 B。

**撤销级联**：撤销事件 = `{cert_digest, revoked_by, ts, sig}`，发到中央
`/api/room-link/delegation/revoke`。中央维护**撤销集**（只有哈希），并向链上
下游各方推送（复用方向 1 的信道，或邮筒）。每个下游 hermes 在每次调用前查本地
缓存的撤销集（Companion 定期从中央同步）。撤销 cert_1 意味着 cert_2、cert_3 全部
失效，因为它们的链回溯会撞上被撤销的哈希。

**发起方的控制**：A 在发起时声明 `max_depth`；A 的 Companion 在"我发出的请求"
列表里能看到链的扩散（中央按 root_task_digest 归集各跳的信封/证书哈希，推给 A）。
A 可以撤销自己的根证书，全链失效。

**审计**：中央存每张证书的哈希、issuer/subject、depth、时间——能画出树，
看不到 reason 和任务内容。

### 2.4 为什么中央看不到却能治理

证书里唯一带业务语义的是 `reason` 和 `root_task_digest` 指向的任务——前者只在
端与端之间传，后者是哈希。中央持有的是证书哈希 + 拓扑 + 撤销集，足以做扩散
监控（"这个任务已经扩散到 7 个人"）、强制收敛（撤销根）、合规审计（谁把谁的
任务委托给了谁），但重建不了任务内容。

### 2.5 攻击与失效场景

| 场景 | 应对 |
|---|---|
| B 伪造"A 让我找你"欺骗 C | cert_1 必须由 A 的机器签名，C 验签；B 造不出 |
| B 想放大权限（parent 只有 dispatch，B 申请 approve） | C 的 Companion 检查单调收窄，直接拒，不呈给本人 |
| A 撤销后 B→C 仍跑 | 撤销集同步有延迟（分钟级）；C 的 hermes 下一次调用前查撤销集即拒；已在跑的那一次由 C 本人停 |
| 撤销集同步不到（C 离线） | C 上线后先同步再接受任何调用；离线期间本来也收不到派工 |
| 环：A→B→C→A | 链上 install_id 去重 |
| 深度炸弹 | max_depth 由发起方定，中央可加全局上限 |
| 中央丢撤销事件 | 撤销方本地也保留，可重发；撤销是幂等的 |

### 2.6 实现落点

- **Companion Rust**：委托证书签发/验证（Ed25519）、撤销集本地缓存与同步。
- **Companion TS**：协同页"等我点头"面板展示委托链；"我发出的请求"展示扩散树；
  发起时选 `max_depth`（默认 0——不许转委托，安全默认）。
- **central**：`delegation_certs`（哈希 + 拓扑）、`revocations` 两张表，两个端点，
  按 root_task_digest 的归集查询。
- **hermes**：零改动。委托证书是 Companion 层的东西，hermes 只见到它熟悉的 grant。
  如果要让 hermes 在每次调用时也查撤销集（而不只靠 Companion 拦），需要 plugin
  patch 在 `/v1/runs` 入口加一个钩子。

工作量：3–4 周，依赖方向 0 的密钥对和目录；撤销推送依赖方向 1 的信道（没有的话
先用邮筒轮询，慢一点）。

### 2.7 权利要求的核心

独立权利要求大意：一种 agent 间任务的多跳委托方法——发起方声明最大委托深度并
签发含任务摘要的根证书；每一跳的资源方在收到委托请求时验证证书链的签名、根一致性、
权限与范围的单调收窄、深度限制与无环，并向本跳资源方本人展示完整委托链后由其
决定是否签发下一跳证书；任一跳签发方可撤销其证书，撤销以证书哈希形式经中央传播，
下游各跳在执行前验证链上无被撤销证书；中央仅存证书哈希与拓扑。

从属：hermes grant 与委托证书的绑定；撤销集本地缓存与离线处理；扩散树回显给发起方；
安全默认 max_depth = 0。

### 2.8 在先技术与区分点

这是三个里在先技术最密的：

- **SPKI/SDSI 证书链、X.509 委托**：证书链 + 收窄的思想早就有。
- **Macaroons / Biscuit**：caveat 只能加不能减，正是"单调收窄"。
- **OAuth 2.0 Token Exchange (RFC 8693)**：委托与 actor 链。
- **UCAN**：去中心化的能力委托链，含撤销。

区分点必须落在：(1) **每一跳有人在环**——资源方本人看到完整链才决定，不是自动
的策略引擎；(2) 证书绑定 **agent 任务上下文**（root_task_digest / prompt_digest），
链是"为了这件事"而不是"给这个身份"；(3) **发起方控制扩散深度并能看到扩散树**；
(4) 撤销经**内容不可见的中央**级联。

风险评估：中高。如果代理人检索后认为 UCAN + 人审批的组合已被覆盖，这个方向可以
降级为方向 1 的从属权利要求（"中继会话策略中的 grant_digest 可为委托链证书"），
不单独申请。

## 3. 员工主权的选择性审计披露（Sovereign Selective Disclosure）

### 3.1 技术问题

审计员要能核查员工 agent 的决策记录（做了什么决定、调了什么工具、给了什么理由），
但公理 1 是员工主权：记录在员工本机，员工有权不给看、有权删自己的数据。现在的
矛盾是：要么员工全给（主权没了），要么不给（审计做不了）；而且就算员工给了一段，
审计员也**无法验证**这一段是完整的、没被事后改过、没被抽掉中间几条。

### 3.2 现状与不够之处

`audit_chain.rs`（P3.3.51）已经给 `decisions.jsonl` 等加了哈希链：每行含
`prev_sha256` 和 `sha256 = SHA256(prev | canonical_json(row))`，配
`decisions.jsonl.chain.json` 记 `{first, last, count}`。`chain_verify` 能报
`broken_at`。UI 上有 `auditViewEnabled` 开关（`store/ui.ts`）让员工决定是否显示
审计视图。

不够之处：

1. **链头无锚定**。链和 `chain.json` 都在员工手里，员工可以从任意位置起重算整条链
   （改一行、重算后面所有 hash、改 chain.json），`chain_verify` 全绿。哈希链只能
   防"不知情的篡改"，防不了持有者自己重建。
2. **无法选择性披露**。给审计员看必须给整段明文；不能只给"某天的决定"而隐藏其他
   天，更不能只给"决定类型和时间"而隐藏"理由原文"。
3. **无法证明完整性**。审计员拿到 20 条，不知道那段时间实际有 20 条还是 35 条。

### 3.3 技术手段

三个部件：

**(a) 锚定（anchoring）**——把链头交给一个员工改不了的地方，但不交内容。

Companion 定期（每小时 / 每 N 条 / 每次 Companion 退出）向中央提交一个**锚**：
`{install_id, log_name, epoch_no, head_sha256, count, ts, sig_install_key}`。中央
只存这一行。从此员工要改锚之前的任何一条记录，都会让重算出的链头对不上中央存的
锚——中央虽不知道链里有什么，但知道"链头应该是什么"。

锚的粒度决定了可篡改窗口：上一个锚之后、下一个锚之前的记录理论上可重建。缩短
锚周期（每条记录都锚 = 实时）以流量换安全，可配。

**(b) 记录级承诺（per-record, per-field commitments）**——让一条记录可以只露一部分。

现在 `sha256` 是对整行 canonical JSON 算的，露一个字段就得露整行。改成：每个
字段单独承诺，记录哈希是字段承诺的哈希：

```
row = { ts, event_type, tool, reason, outcome, ... }
for each field f:  c_f = SHA256(salt_f | value_f)      # salt_f 随机, 存本机
row_hash = SHA256(prev | c_ts | c_event_type | c_tool | c_reason | ...)   # 字段顺序固定
```

披露时，对想露的字段给 `(value, salt)`，对不想露的只给 `c_f`。审计员能重算
`row_hash` 验证整行没改，但对没给 salt 的字段一无所知（salt 让哈希不可字典攻击）。
这就是**可编辑的签名记录**（redactable record）的一个最简形态。

**(c) 范围证明（range proof over the chain）**——证明"这一段是连续的、完整的"。

员工披露区间 `[i, j]`：给出第 i−1 条的 `row_hash`（作为起点）、第 i..j 条的记录
（按 (b) 部分披露）、以及从第 j 条到最近一个锚之间所有记录的 `row_hash`（不给内容）。
审计员从起点重算到锚，跟中央的锚比对。通过则证明：区间内每一条都没改、区间内没有
被抽掉的记录（抽一条链就断）、区间外的记录数量也对（锚的 count）。

如果链很长，"从 j 到锚的所有 row_hash"会很多；可以改成每个 epoch 内建 Merkle 树，
锚存树根，披露时给 Merkle 路径，证明体积变成 O(log n)。MVP 先用链，够用。

**员工侧的操作**：审计视图里选时间段 → 选要露的字段（默认露类型/时间/工具名，
隐藏理由原文和内容摘要）→ 生成"披露包"（记录 + salt + 哈希路径 + 引用的锚号）→
导出文件或经中央转给审计员（中央只是搬运，内容对中央仍是密文，可复用方向 1 的
信封）。审计员用一个独立的校验工具（或 web 后台的一页）导入披露包 + 从中央拉锚
→ 出验证报告：多少条、多少条完整披露、多少条部分披露、链是否完整、锚是否匹配。

### 3.4 为什么中央看不到却能治理

中央持有的是每个员工每个日志的**锚序列**（链头哈希 + 计数 + 时间），这足以：
证明记录未被事后改写（哈希对不上）、证明记录未被删除（计数对不上）、给审计员一个
不受员工控制的参照点。但锚是单向哈希，中央从中重建不出任何一条记录。

员工主权体现在：披露由员工发起、员工选范围、员工选字段；不披露的部分审计员只能
知道"存在且未被改"，不知道内容。这跟"员工有权删自己数据"也兼容——删除后链会断，
审计员看到的是"这里被删过"，而不是"这里什么都没有"，公理 1 的原文就是"审计员要
看出被改过"。

### 3.5 攻击与失效场景

| 场景 | 应对 |
|---|---|
| 员工在两个锚之间改记录再重算 | 窗口受锚周期限制；可配实时锚；改动会改变 count 时立即暴露 |
| 员工不上传锚（断网 / 关掉） | 中央看到锚缺失的时段，审计报告标"此段无锚，不可验证"——不是通过，是显式的未知 |
| 员工伪造锚 | 锚由安装私钥签名，中央验签 |
| 中央篡改锚 | 锚有员工签名，员工本地也留副本，可对质 |
| 字段 salt 丢失 | 该字段无法披露（只能证明存在）；salt 跟记录同文件存 |
| 审计员要求全量 | 那是管理问题不是技术问题；技术上保证的是"部分披露也可验证"，不阻止全量 |
| 两台机器同一员工 | 每台独立链、独立锚，install_id 区分 |

### 3.6 实现落点

- **Companion Rust**：`audit_chain.rs` 改为字段级承诺（向后兼容：老行整行哈希，
  新行字段哈希，chain.json 记格式版本）；锚上报（定时 + 退出时）；披露包生成
  （范围 + 字段选择 + 哈希路径）。
- **Companion TS**：审计视图加"披露"流程（选段、选字段、导出）。
- **central**：`audit_anchors` 表 + `/api/audit/anchor`（POST，员工 OIDC 身份）+
  `/api/audit/anchors?install_id&log`（审计员角色查询）。
- **web 后台**：审计员页"导入披露包 → 校验报告"。
- **hermes**：零改动。

工作量：2–3 周。只依赖方向 0 的密钥对，不依赖方向 1、2。

### 3.7 权利要求的核心

独立权利要求大意：一种端侧记录的可验证选择性披露方法——端侧对记录逐字段生成带
随机盐的承诺并以承诺序列构成链式哈希；端侧周期性向中央提交由端侧签名的链头哈希与
记录计数作为锚，中央仅存锚；披露时端侧对选定记录区间给出选定字段的明文与盐、
未选字段的承诺、以及区间末端到最近锚之间的哈希路径；验证方据此重算至锚并与中央
留存的锚比对，从而在不获得未披露内容的情况下验证已披露记录的完整性、连续性与
未被篡改。

从属：Merkle 树替代线性路径；锚周期可配；删除留痕的语义；披露包经内容不可见的
中央转交。

### 3.8 在先技术与区分点

- **Certificate Transparency / 透明日志**：Merkle 树 + 公开审计，但日志内容公开。
  区分点：内容留在端侧，中央只锚。
- **可编辑签名（redactable signatures）**：字段级披露的密码学基础，学术上成熟。
  区分点：与链式哈希 + 中央锚定 + 计数完整性的组合，应用于端侧 agent 决策日志。
- **区块链存证**：把哈希上链。区分点：不需要链，中央就是锚存储；且有选择性披露
  与范围完整性证明，存证方案通常只做"这个哈希在这个时间存在"。
- **企业 EDR / SIEM 日志**：全量上传，没有主权。

风险评估：中低。单个部件都是已知技术，但"端侧持有 + 中央盲锚 + 字段级选择披露 +
范围完整性 + 删除可见"这一组合在"员工 AI agent 决策审计"这个场景下我没见过现成
的。这个方向的工程价值也很实在：它把"员工主权"从产品口号变成合规评审能看懂的机制，
政企客户的安全部门会买账。

## 4. 三者的关系与建议顺序

```
方向 0  安装密钥对 + 中央公钥目录         ← 全部依赖，先做，1 周
   │
   ├─ 方向 1  盲中继（信封承诺 + 会话策略）   ← 多机协同跨网段的前提，2–3 周
   │     └─ 方向 2  多跳委托（撤销推送复用 1 的信道）   ← 3–4 周，专利风险最高
   │
   └─ 方向 3  选择性审计披露（锚 + 字段承诺）   ← 独立于 1、2，2–3 周
```

建议：

1. **先做 0 + 1**。1 是产品必须的（不做就只能同内网用），专利是顺带。做完就能
   写第一份交底书，此时申请最早，公开风险最小。
2. **3 紧随其后**。它不依赖 1，可以并行；工程小、专利风险低、对政企安全评审的
   说服力强。
3. **2 先不做**。等 1 上线、真有员工提出"我的 agent 需要找第三个人"的需求再做。
   专利上它最可能被在先技术覆盖，做出来也可能只是 1 的从属项。

如果三个都做，最强的申请策略不是三件，而是**一件主专利 + 分案**：主专利写"中央
不可见内容的可治理端侧协作方法"（第 0 节的原语），三个方向作为三个实施例；代理人
根据检索结果决定哪些实施例值得分案独立申请。这样即使 2 被否，1 和 3 还在同一
个保护伞下。

## 6. 在先技术检索结果（2026-09-15）

只用了公开网络检索（Google Patents、IETF、arXiv、厂商文档），没有查 CNIPA 数据库
全文，也没有专业检索工具。但下面列的每一条都是直接命中，足以下结论。

### 6.1 方向 2 多跳委托 —— 已被标准草案和论文完整覆盖，放弃

- **IETF `draft-niyikiza-oauth-attenuating-agent-tokens-01`**（2026-06-15，Tenuo）：
  "Attenuating Authorization Tokens for Agentic Delegation Chains"。任务范围的签名
  委托凭证，`del_depth` / `del_max_depth` 字段限制委托深度，持有者可离线派生权限
  只收不放的子令牌，链可由任何持有根信任锚的执行点离线验证，第 8.9 节撤销。
  这就是 2.3 节的委托证书，连字段名都几乎一样。
- **HDP: Human Delegation Provenance**（arXiv 2604.04522，2026-04）：记录人类
  委托者及其声明范围，每一跳累加一条 Ed25519 签名的 hop record，任何接收方凭
  签发者公钥验证完整链。覆盖了 2.8 节我押的"每一跳有人在环"这个区分点。
- **NovaVey/Attenuated-Delegation-Chain**（GitHub）：biscuit 风格的 AI agent
  委托凭证，每跳只能收窄，附差分模糊测试证明。开源实现。
- **Agent Control Protocol**（arXiv 2603.18829）、WorkOS / Okta / TrueFoundry
  2025–2026 的博客：多跳委托问题已是业界共识话题。

结论：新颖性没有了。IETF 草案是 6 月公开的，任何人现在申请都会被它驳。工程上
反而是好消息——**直接采用 AAT 格式**，省一套自己设计的协议。

### 6.2 方向 3 选择性审计披露 —— 核心机制是 Palantir 2018 年的已授权专利，放弃

- **US11032065B2 "Verifiable redactable audit log"**（Palantir，优先权 2018-06-14，
  授权 2021-06-08；延续案 US11849023B2）：哈希链日志，用 **salt** 让被编辑掉的条目
  不可被字典猜测，支持段级编辑，编辑后链仍可验证。3.3 节的 (b) 字段级带盐承诺和
  (c) 范围证明，就是这个专利的权利要求范围。
- **VCT: A Verifiable Transcript System for LLM Conversations**（arXiv 2606.23003，
  2026-06）：针对 LLM 对话的三层结构（问答对哈希链 → 会话 Merkle 根 → 账户级
  Merkle 根 + 联合签名锚定），支持**选择性分享**、多设备、对恶意服务器视图分叉的
  检测与不可抵赖取证。连"应用于 LLM 对话记录"这个场景限定都被占了。
- 链头外部锚定（CT 透明日志、时间戳机构、KSI）是教科书做法。
- **US8230228B2**（日志篡改检测）、**US10581613B2**（多跳前后向链接的可验证
  数据结构）等早期专利也在。

结论：能写的独立权利要求只剩"员工发起、中央盲锚、计数完整性"这层皮，创造性
过不了。工程上仍值得做——它是公理 1 落地的机制——但按 Palantir 专利做要注意
中国境内是否有对应族（US11032065 未查到 CN 同族，需代理人确认）。

### 6.3 方向 1 盲中继 —— 每个部件都有在先技术，组合创造性存疑，不建议单独申请

- **Cisco AGNTCY SLIM**（IETF `draft-mpsb-agntcy-slim`，GitHub agntcy/slim）：
  数据面节点**只按元数据转发**，MLS 端到端加密，节点不参与会话、读不到内容，
  另有控制面做编排。这就是 1.3 节的"盲中继 + 信封路由"。
- **Google Agent Gateway**（Gemini Enterprise Agent Platform）：对 A2A / MCP 流量
  按属性做授权策略——但它看内容。
- **AgentCrypt**（JPMorgan AI Research，arXiv 2512.08104，2025-12）：中间 agent
  只中转密文、身份基加密的策略化访问，在 LangGraph / Google ADK + A2A 上实现。
- 中间方存哈希 + 签名做不可抵赖：**US8656166**、**WO2001025883A2** 等 2000 年
  前后的专利。
- "Communication-Graph Metadata in Autonomous Agent Interoperability"
  （arXiv 2606.07150，2026-06）明确指出 SLIM 等都不隐藏通信图——跟我们 1.5 节
  承认的元数据泄露是同一件事，说明这个边界业界已经画清楚了。

没有单篇覆盖"资源方签名的会话策略由盲中继执行 + 中继留存签名承诺 + 资源方撤销"
这个组合。但审查员把 SLIM（盲转发）+ Agent Gateway（元数据策略）+ 非抵赖哈希
三件叠起来就能否创造性，胜算不大。

结论：工程上**必须做**（否则多机协同只能同内网用），但建议**在 SLIM 上做而不是
自己造**——它已经解决了盲转发、MLS 群密钥、多节点；我们只需加会话策略和承诺
留痕两层。专利不单独申请。

### 6.4 修正后的判断

| 方向 | 在先技术 | 专利 | 工程 |
|---|---|---|---|
| 1 盲中继 | SLIM / AgentCrypt / Agent Gateway / 非抵赖哈希 | 不申请 | 做，基于 SLIM |
| 2 多跳委托 | IETF AAT 草案 / HDP / 开源实现 | 不申请 | 需要时直接用 AAT |
| 3 选择性披露 | Palantir US11032065 / VCT / CT | 不申请 | 做，注意 Palantir 专利边界 |

第 4 节说的"一件主专利 + 三个实施例"也不成立：主专利的原语（端侧签名承诺 +
中央盲存）就是 SLIM + 非抵赖哈希的组合，没有独立于三个实施例的新贡献。

上一条回复里我说"1 和 3 站得住"，是没查就下的判断，错了。这个领域 2025 下半年到
2026 上半年出了一批标准草案和论文，节奏比我的印象快得多。

### 6.5 那还有什么

诚实的答案：**以现在的产品，没有值得申请的发明专利。** 竞争壁垒在交付能力和
政企场景的整体集成，不在任何单个机制上；而单个机制层面，业界在 2026 年已经把
agent 授权、审计、加密通信这几块的地基铺完了，我们该做的是站上去，不是重铺。

如果一定要有知识产权数量：软著（Companion / gateway / identity 三件）照登记；
发明专利等真正做出别人没有的东西再说，现在为申请而申请只会交一笔代理费换一张
驳回通知书。
