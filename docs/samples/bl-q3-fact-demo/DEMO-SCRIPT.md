## Step 1 (0:00-1:30) — 铺垫: 为啥需要这个

**关键提问** (打开客户痛感):

> "贵司每个季度有多少次政策 / 标准 / 流程的更新?"
>
> "员工怎么知道这些更新? 多久能让所有相关员工真正按新规执行?"
>
> "审计的时候, 你们怎么证明'确实落实到每个员工的日常操作'?"

**预期客户答案**: "每季度 5-10 次更新 / 邮件群发或部门会通知 / 主要靠人工巡查".

**铺垫话术**:

> "这就是 catfish 想解的问题. 通用 LLM (ChatGPT / Claude / 国内闭源) 永远卡在某个训练时间点, 不可能知道贵司**昨天**新发的财务流程. 而你们用的 SAP / 飞书 / 钉钉, 知道政策但不会**改员工的日常工具**.
>
> catfish 在这中间 — 我们既是员工日常打开 N 次/天的桌面工具, 又能跟着贵司一起更新. 接下来 5 分钟我演示这个机制."

---

## Step 2 (1:30-3:30) — 现状: catfish 已经在做的"持续学习"

**操作**: 打开 Companion → Dashboard → **LearningCard**

**讲解**:

> "您看, 鲶鱼装到您电脑上之后, 它**会成长**. 这不是营销话术 — 这是个真实在跑的机制.
>
> 它会自检自己上次干的事 (比如帮员工写周报、做表格), 觉得'我这个 skill 应该改进'就提一个改进建议 (point at SkillRevisionCard pending 状态).
>
> 员工 (或合规) 点'采纳' → 进 **14 天有效性追踪** (point at BL-MM15). 如果 14 天内 skill 输出质量没改善, 鲶鱼会主动建议回退. 这是真的 stability-plasticity 控制."

(切到 catfish-web 后台 `/admin/system`)

> "在管理员视角, 这是全公司的 skill 改进活动. 您看到这些时间戳 / 采纳率 / 谁审批的 — 全程可审计. 央企的合规边界, 我们一开始就考虑了."

**铺垫结束**: "现状是**反应式的** — 员工反馈了鲶鱼才反思. 但很多政策变更员工自己都不知道, 怎么反馈? 这就是接下来要演的 BL-Q3-FACT."

## Step 3 (3:30-7:00) — 主菜: 政策变更 → 自动同步

**步骤 3.1** (5 秒): 切到 catfish-web `/admin/facts`

> "假设我是合规专员小李, 国家网信办上周发了《数据出境安全评估办法》修订稿. 我把它丢给鲶鱼."

**步骤 3.2** (15 秒): 点"选择文件" → 上传 `policy-purchase-revision.md` → 标题填 "公司采购流程修订 v3.2" → 点"上传 + 分析"

> "我刚上传的是一份示例的'公司采购流程修订'文件, 改了几条规则 — 比如审批阈值 5 万改 3 万, 季度采购计划提前申报从 2 周改到 3 周, 还加了 ISO 27001 资质等."

**步骤 3.3** (30-90 秒): 自动跳详情页 → 看转圈 → 等 LLM 分析

> "鲶鱼现在在做三件事 (point at 进度提示):
> 1. **解析这份文件**, 提取出可执行的'事实变更' (不是泛泛的摘要)
> 2. **拉公司 SkillsHub 的全部 skill**, 找受影响的
> 3. **对每个受影响的 skill 生成改进 patch**, 可以直接采纳发布
>
> 这个过程一般 30 秒到 2 分钟. 我们等等."

**步骤 3.4** (30 秒): 分析完成, 展示**提取的事实点**

> "鲶鱼读完文件, 提取出 5 个**可执行**的事实点:
>
> 1. 采购阈值 5 万 → 3 万
> 2. 急采购需 CFO 二次签字
> 3. 供应商加 ISO 27001 资质
> 4. 季度计划提前 2 周 → 3 周
> 5. 进口设备加海关清单
>
> 注意, 每条都带**原文引用** (展开一个事实点的'原文引用' details) — 不是 LLM 自己编的, 是真从原文逐字摘录的. 审批员可以一眼对照原文."

**步骤 3.5** (45 秒): 展示**受影响 skill**

> "鲶鱼接着扫了我们 SkillsHub 上所有 skill, 找出 2 个受影响 (point at impacts):
>
> - **skill-send-purchase-request** confidence 95% — 它的逻辑里写着 '5 万以上要总监审批', 现在跟新规的 3 万冲突
> - **skill-quarterly-budget-review** confidence 75% — 它默认提前 2 周报送预算
>
> 还有一个 skill-vendor-onboarding 没被命中 — 因为它的内容**已经包含**了 ISO 27001 (v2.0 已经升级过). 这说明 FACT **不误报**, 不会拿已经合规的 skill 来烦审批员."

**步骤 3.6** (45 秒): 展开**第一个 patch 对照**

> "鲶鱼对每个受影响的 skill 生成了改进版. 您看这个 patch (展开 skill-send-purchase-request 的 changes):
>
> (point at diff 红绿对照)
>
> 红色是原内容, 绿色是改后. 不仅改了阈值, 还改了 error handling 那段的警告文字, 全部跟新政策对齐. 改的理由这里 (point at rationale) — 引用了原文'采购阈值 5 万 → 3 万'.
>
> 我作为合规, 看 30 秒就能判断这个 patch 对不对. 对就采纳."

**步骤 3.7** (10 秒): 点"采纳 → 发布到 SkillsHub" → 确认弹窗 → 等 publish → 弹"已发布新版本 1.0.fact-xxxxxxxx"

> "采纳了. 新版 skill 已经发布到 SkillsHub. 装了这个 skill 的员工, 下次打开 Companion 就会装到新版 — 自动遵守新规."

**(可选) Step 3.8** (15 秒): 点采购部那个员工的 Companion → SkillsMcpCard → 显示 skill 版本 1.0.fact-xxxxxxxx

> "您看, 在采购部小王的 Companion 上, skill 已经是新版了. 接下来他写采购单, 阈值就是 3 万, 不需要小王自己知道新规.
>
> **这就是 catfish 的核心**: 让员工不知不觉跟上公司变化, 而合规可以一眼看到全公司同步覆盖率."

## Step 4 (7:00-9:00) — 升华: 为啥只有 catfish 能做

**关键论点** (按重要性排):

> "这事**通用 LLM 永远做不了**, 三个根本原因:
>
> 1. **他们不知道贵司内部规则** — ChatGPT 不可能学到'贵司财务流程修订 v3.2'
> 2. **他们没'在客户公司里运行'的概念** — 训练-部署-推理三段式, 客户私有知识进不了训练
> 3. **他们做了也卖不出去** — 通用厂家卖的是通用能力, 不是贴贵司流程
>
> **企业知识库厂家** (飞书 / 钉钉 / 蓝凌) 也做不了, 因为他们没'白盒可执行 skill'这个层. 知识库 + LLM = 问答, 不是改员工日常工具.
>
> catfish 站在中间这个真空: 既是员工日常工具 (Companion 每天打开 N 次), 又是白盒可改 skill 体系 (这次演示的). 这两条加起来才能做 fact patch."

**白盒可审计的强调** (合规客户特别敏感):

> "另外重点说一下白盒. 我刚刚演示的整个流程, 您能在 `/admin/facts/{id}` 看到完整的操作审计 (打开 audit log 给客户看) — 谁上传 / 几点解析 / LLM 找了哪些 skill / 谁采纳 / 发布的什么版本.
>
> 这个跟改 LLM 权重的方案完全不一样. 那种'让 AI 自动学'的路子有个致命问题: **学完之后没人知道它学了什么**, 央企合规过不了. 我们走 module 层 (改 skill 文件), 而不是 weight 层 (改模型权重), 就是因为这个差异."

## Step 5 (9:00+) — Q&A 应对

### Q: 你们多久能让这个 Q3 启动?

> "我们刚把 P0 MVP 做出来 (就是您刚看到的演示版). Q3 启动的是生产级:
>
> - P1 (Q3 第 3-4 周): 自动扫公司知识库 (接 mcp), 不需要手动上传
> - P2 (Q4): 合规专属审批 workflow + 跨子公司 federation
>
> 您如果有兴趣, **Q3 联合试点**是最好的方式 — 您出一份真实政策文件 + 您部门 5-10 个 skill, 我们一起跑一遍. 您评估准确率, 我们根据您反馈调."

### Q: LLM 会不会瞎改我们的 skill?

> "三层保险:
>
> 1. **prompt 强制**: LLM 改 skill 时只能引用 raw_quote (原文摘录), 不能引入额外知识. 您可以打开任何一个 patch 的'理由'看 — 都引用原文.
> 2. **confidence 阈值**: 默认 0.6 以下不生成 patch.
> 3. **必经人工审批**: 没有'自动落盘'选项. 这个跟您刚看到的一致 — 弹窗确认 + 显式点采纳."

### Q: 我们用自己的 LLM 行不行? 数据上云?

> "FACT 系统**整个流程 100% 本地**. 您看 (point at internal_models.py 注释): catfish 用 LLM 是按 use_case 选, 默认**tier=private 优先**. 您接的私有 deepseek / 千问内网部署的, FACT 就用您的. 数据完全不出您公司."

### Q: skill 改坏了怎么办?

> "您看每个改完的 patch 都自动进入 **14 天有效性追踪** (point at LearningCard BL-MM15). 14 天内如果 skill 输出质量没改善, 鲶鱼主动建议回退. 这是个软回滚 — 不会强制员工换回去, 但会出现在他的 LearningCard 里. 真严重的话, sysadmin 可以直接在 `/admin/skills` 删那个版本, SkillsHub 自动回退到上一个."

### Q: 价格?

> "FACT 我们计划作为**合规增值模块**单独定价 (跟基础包分开). 具体定价方式我们 5/15 之后跟您聊, 大致原则是按'政策变更 × 受影响 skill 数'累进 或 包年制. 您如果是大量合规需求, 包年更划算."

### Q: 如果我们想 Q3 一起做, 我们要准备什么?

> "三件事:
> 1. **2-3 份**真实政策文件 (我们一起脱敏 + 跑分析, 评估 LLM 准确率)
> 2. **5-10 个**贵司高频用的 skill (让 LLM 真扫一遍)
> 3. **1 位**合规对接人 (跟我们一起 review 第一批 patch)
>
> 我们这边出: P1 工程 (1-2 周) + 现场支持. 您评估觉得准确率达标 → Q4 正式上线."

## 现场救场剧本 (万一出意外)

### 救场 1: LLM 分析失败 (网络 / 配额)

不要紧张, 切到设计文档讲架构图. 客户对设计文档 + 演示视频 (你提前录的) 同等满意.

```
"网络环境略不稳, 我先讲下架构 (打开 CATFISH-FACT-PATCH-DESIGN.md 第四章).
回头我发您一份演示视频 + 设计文档完整版. Q3 联合试点时一定让您看实时跑一遍."
```

### 救场 2: 上传后转圈太久 (> 3 分钟)

```
"我们今天给您的 demo 是用 deepseek-flash 这种轻量模型, 跑得快但精度略低.
真生产您用千问 max 或 GPT-4 量级, 会快 + 准. 我先把已经分析好的另一个 fact 给您看
(切到提前准备好的另一个 fact 详情页)."
```

### 救场 3: 客户问 5/14 不该问的 Q3 P2 细节

```
"这个问题非常好, 但今天我先把 P0 MVP 给您看清楚, 因为这是已经能跑的.
P2 您说的那个 (合规专属审批 / 法律风险标注), 我们 6 月再约一次专门讲 — 那时候
我们刚跟另外两家试点客户跑完, 数据更扎实."
```

## 演示后跟进

5/14 当天结束后:
1. 把 `docs/CATFISH-FACT-PATCH-DESIGN.md` 完整设计文档发客户
2. 录的演示视频也发一份 (备份)
3. 7 天内约下次会议, 谈 Q3 联合试点 ToR (Terms of Reference)
4. 内部回顾: 客户问了什么没回答好? 是不是设计文档要补?

**最重要的一句**: 客户在 5/14 不需要做决定. 他们需要的是**"觉得这个方向对"**. 你的目标是让他离开会议时, **跟同事说"catfish 那家挺有意思, 我们试试"**. 决策签合同是 Q3 的事.
