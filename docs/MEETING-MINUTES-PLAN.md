> 10/1 定稿。鸿波拍板: Chromium 保持内嵌; 旧录音并入会议功能、删除 whisper;
> 参会人数必填; 音频默认留 7 天; P1 不做实时字幕; 先只支持 Apple Silicon。

## 2. 选型依据 (本机实测, M4 / 16G, CPU)

FunASR: FSMN-VAD + SeACo-Paraformer (支持热词) + CT-Transformer 标点 + CAM++ 说话人, 全部 Apache-2.0。

| 项 | 结果 |
|---|---|
| 2 分钟 4 人样本 | 15s 转完 (~8× 实时), 分出 4 人, 文本/标点质量好 |
| 30 分钟 | 3.5 分钟; 加载 24s; 峰值内存 3.7GB |
| 说话人, 不给人数 | **30 分钟时分出 42 人** (实际 4 人) |
| 说话人, `preset_spk_num=4` | 4 人; 同一人跨时段标签一致 ~92% |
| 体积 | torch 等 ~0.65GB + 模型 2.1GB (识别 954M / 标点 1.1G / 说话人 28M / VAD 4M) |

→ 参会人数必填; 组件包 ~2.7GB 不进安装包 (现在安装包 ~600MB)。

文档对比 (阿里官方图, 读图近似): WenetSpeech 会议集字错率 whisper-small ~24.8% vs Paraformer-zh ~6.9%。

## 3. 架构

```
录音 (Rust, cpal) ──► ~/.catfish/meetings/<id>/audio/*.wav (5 分钟一片)
        │
        ▼ 会后
转写 (独立 Python 环境 ~/.catfish/meeting-asr/venv, 按需起子进程)
        │  输入: 切片 + 参会人数 + 热词 (wiki 人物/项目标题+别名 + 手填)
        ▼  输出: transcript.json (段: spk / start / end / text)
说话人改名 (界面)
        │
        ▼
纪要 (tool-bridge `meeting/*` RPC → 中央大模型, 员工当前选的模型)
        │  输出: 摘要 / 决议 / 待办(负责人·事项·截止) / 待定问题 → minutes.md
        ▼
写回 (用户确认): 待办 → 任务库 (source=meeting, 幂等); 存知识库 → wiki_ingest
```

要点:

- **录音用 Rust (cpal) 直接录**, 不再依赖 brew 的 ffmpeg; 设备按名字选 (序号会变)。
  聊天 🎤、RecMode 旁白、会议共用这一个录音模块。
- **转写环境独立**, 不进 `hermes-extra-packages.txt` —— 那份清单是全有或全无,
  且每次启动都 import 检查, 加 torch 会拖慢所有人的启动。
- **纪要走 RPC 白名单** (照 `recmode_rpc` 的 `recmode/` 前缀写法), 不进小鲶的工具列表。
- **数据**: 音频 / 转写 / 纪要只在 `~/.catfish/meetings/`; 只有转写文字经网关去大模型 (网关不落盘,
  符合 CENTRAL-EDGE-DATA-BOUNDARY)。隐私卡片加这一项。
- **删除 whisper**: `speech.rs` 的 whisper 链路、`parse_file_audio.py`、聊天上传音频
  (`transcribe_audio_from_b64`) 全部改走会议转写; 组件包没装时 🎤 提示去装。
  上传的音频文件 = "导入一场会议"。

## 4. 组件分发 (P0)

内嵌 vs 服务器按"启动必需 vs 功能可选"切:

- 留在安装包: Python / uv / hermes / hermes 依赖 / node / Chromium (启动必需或鸿波定为必须)。
- 放中央: 会议组件包, 以及以后的 bge-m3 向量模型、语音包等 (现在都要员工手动 curl)。

中央: catfish-web 的 nginx 加 `location /components/` 静态托管, 目录挂载到宿主机;
`manifest.json` 记每个组件的 name / version / platform / file / size / sha256。

客户端: 读 manifest → 断点续传下载到 `~/.catfish/runtime/` → 校验 sha256 → 原子改名。
断网机器沿用"IT 手动把包放进 `~/.catfish/runtime/`"(现有解析逻辑已支持该目录)。

## 6. 已知风险

- 峰值内存 3.7GB / 30 分钟: 16G 机器开很多应用时可能吃紧 → 转写在会后跑, 进程降优先级, 界面提示。
- 说话人编号是"本场录音内匿名", 不是人物识别; 抢话片段会错, 由人改名 + 大模型按上下文纠正。
- 1–4 的速度数据来自 M4; 更老的 M1 需要实测。
- manifest 的 sha256 只防损坏不防篡改 (同一通道下发); 内网 HTTPS + 中央证书信任先顶着, 签名 (minisign) 后续加。

## 8. 会中小鲶 (11/15, Companion 1.2.192)

鸿波 11/15 问「会议期间是不是也应该支持小鲶随时的支持」。定下来: 边录边转 + 随时问 + 小鲶主动提示, 都只给员工自己看。

- **边录边转** (`src-tauri/scripts/meeting_asr_live.py`, Rust `services/meeting_live.rs`): 开始录音时 (装了会议组件包) 起一个常驻进程,
  模型只加载一次 (~17 秒), 每 10 秒把各音轨新录到的认一遍, 追加 `live_transcript.jsonl`。窗口切在句子边界 (除最后一句都提交,
  最后一句下次连同新录的重认); 一次最多 90 秒, 落后超过 60 秒界面说「跟不上」。2 线程 + nice 10。不分说话人 (会后照常整场重转);
  线上会议两条音轨分开认, 麦克风那条去回声。结束录音 = 关它的 stdin, 它把剩下的认完自己退, 90 秒没退就杀掉。
  实测 (M4): 30 秒音频 1.5 秒认完; 一场真会议的 120 秒录音按 4 倍速写进分片边写边认, 42 句首尾相接无重叠无缺口。
  **没用流式 Paraformer** (原 P3 设想): 给意见要上下文, 延迟 1 秒和 30 秒差别不大; 换流式要往组件包加模型、Windows 重打包。
- **问小鲶** (tool-bridge `meeting_live.py`, JSON-RPC `meeting/live_assist` kind=ask): 会议页右边录音中显示实时文字 + 输入框;
  小鲶看到目前为止的会中文字 (最近一万字) + 「最近 2 分钟」(「刚才」) + 知识库里提到的条目 + 上次同系列会议遗留 (跟纪要同一份背景)。
  点实时文字里的一句 = 问框里先填「关于 [12:30]「…」: 」。
- **主动提示** (kind=hint, 默认开, 录音中可以关, 存 `meta.live_hints`): 会议页开着时每 3 分钟看一眼上次之后新说的话 (不到 60 字不调模型),
  只挑真有的出卡: 决议 / 待办 / 没人答的问题 / 跟资料对不上 (要背景材料有明确依据) / 可以追问; 已提示过的不重复。
- **记到纪要**: 每条提示、每个问答可以「记到纪要」或「忽略」(`live_notes.json`, `meeting/live_note`)。生成纪要时记下的作为
  「员工会中确认过的要点」给大模型 (转写对得上才写进决议 / 待办), 纪要末尾附「## 会中小鲶」; 会后纪要旁边「会中小鲶」可以改记不记、删,
  固定格式的纪要跟着改 (按模版写的要重新生成)。
- 数据边界跟纪要一样: 录音不出本机; 会中文字只在问小鲶 / 主动提示时经网关给大模型 (员工自己的身份), 别人的话只当材料。
- **先查本机资料 (11/15, 1.2.193, tool-bridge `local_lookup.py`)**: 鸿波在群里「@小鲶 ITSS 一级现状」, 小鲶只看了群聊记录答「不知道」。
  现在群聊「@小鲶」和会中问小鲶都先查: 大模型从问题里提 1–3 个搜索词 → 知识库 (wiki_search: 关键字 + 语义 + 关系一跳, 跟主对话同一套;
  每词先取 6 条, 按标题跟问题的贴合度重排留 4 条 —— 原排序会把提到它的人物条目排在本条前面) + 本机文件 (search.db 全文, 取命中处前后一段)
  + 邮件 (标题 / 发件人 / 时间)。长条目不从头截: 语义命中的那一段放最前, 再按小节挑「最上面的当前状态」、跟问题对得上的节、最后一节
  (常是最新通知), 每条约 2200 字。回答下面列「依据 (你电脑上的)」。
- **会议里的知识库背景也改了 (11/15, 1.2.194, `meeting_context.wiki_context`)**: 会中主动提示、会后纪要原来只认「条目名 / 别名原样出现」,
  每条从头截 600 字。会上说「一级答辩改到 18 号」关联不上「ITSS运维服务能力成熟度一级」(没人说全称, 条目没别名); 关联上了也只看到开头的
  基本信息表, 提示不出「跟资料对不上」。现在: 名字对上的优先, 再把会上的话按 1200 字一段 (长会议均匀取 12 段) 送进知识库混合检索补最多 4 条;
  每条按小节挑 (语义命中段 / 最上面的当前状态 / 跟会上提到它的那几句对得上的节 / 最后一节), 每条约 1500 字, 合计 7000 字。
- **会中中断两处修正 (11/16, 1.2.197)**: 鸿波 11/16 下午连开的几场会里查到两种「中断」:
  ① 实时转写开会 7 分半就停了 —— 一段 30 秒都没人说话时 FunASR (VAD 一句没切出来) 返回空列表, `generate(...)[0]` IndexError,
  整场没了实时文字 (录音本身没事)。现在空结果当作这段没人说话; 某一段识别出错也只跳过那段 (连续 5 段都失败才放弃)。
  拿那场会的真实录音复现、修后同一段不再崩。
  ② AirPods 断开 (日志「录音流出错: Device disconnected」) 后 17 分钟没录到: 原来只记一句红字, 录音线程接着空等, 计时停住、
  电平停在断开前那一下 (「没收到声音」也不提示), 看着在录其实没录。现在 (services/meeting_recorder.rs) 设备报断开、或 6 秒
  收不到一块数据, 就收掉这一片、换系统默认麦克风 (如 MacBook 自带) 在同一场会里接着录, 新开一片 (采样率可以不同), 断开到接上
  补静音对齐时间; 界面提示「「AirPods」断开了, 已自动换成「MacBook Air 麦克风」接着录 (中间约 N 秒没录到)」、设备名跟着变;
  一个麦克风都没有时每秒重试, 红字「在等可用的麦克风」, 电平归零。真断开要在真机上验 (摘 AirPods)。
- **转写的句子时间越往后越早 (11/16, 1.2.199)**: 鸿波「点 ▶ 听那一句, 文字要滞后声音」。查下来 FunASR 1.4.16 拼出来的
  sentence_info 时间逐渐往前偏: 18 分钟的会第 400 秒说的「你们都写成 CBT…」被标在 361 秒 (切口测试: 从第 400 秒切开单独认,
  第一句就是它), 两个多小时的合并会议后面偏好几分钟; 说话人也是按这个错的时间分的。逐字时间戳 (result["timestamp"]) 是准的、
  字数也一一对得上 —— 错在它拼句子那一步。现在 meeting_asr.py 截下它内部的说话人分段 (distribute_spk 的入参), 自己按标点
  切句子、起止取首尾字的时间、按重叠分说话人; 对不上 (少见的字符) 退回原来的。实时转写同样处理。
  同一场会重转后抽查 120 / 400 / 700 / 1000 秒: 偏差从 -15 / -40 / -65 / -95 秒都变成 0。已转写的三场会用新脚本重转了
  (原来的存成 transcript.before-1116.json), 纪要只用文字, 不受影响。
  字数跟时间戳对不上时 (1.2.200) 也不再整场退回 FunASR 的句子: 按位置对齐 (第 i 个字取第 round(i×(m-1)/(n-1)) 个时间戳),
  差超过一成才退回。真实结果里人为删 3 / 20 / 100 个时间戳 (0.1% / 0.8% / 4.1%): 句子起点平均误差 0.11 / 0.53 / 1.1 秒,
  最大 2.6 / 3.6 / 4.5 秒 (长停顿前后), 后半段跟前半段一样, 不会越往后越偏。

## 10. 说话人分得更准 (11/17, Companion 1.2.205)

鸿波 11/17: 「模型是不是对多人的混音没有处理能力?」—— 是的: FunASR 一条混音进来, 每句只归一个人, 没有重叠检测 / 人声分离。
这次做的是「A: 不加模型, 把说话人分对」(B 人声分离太慢、C 云端转写要把录音发出去, 都没做)。

**原因 (读 FunASR 1.4.16 源码)**: 给了人数 (preset_spk_num) 时, 声纹片段 < 2048 个走谱聚类, **≥ 2048 个 (半小时以上的会) 走
KMeans 硬分成 N 簇**, 而且给了人数就跳过它自己「声音很像的并掉」那步。CCRC 整改会 (2:12, 填 10 人) 4108 个片段被硬切成 10 簇,
每簇 290–643 个, 平均得不像真会议。不填人数又走 UMAP+HDBSCAN, 长会议会拆出几十个 —— 所以人数还是必填, 但现在是**上限**:
- meeting_asr.py `ClusterRefine` 包住 FunASR 的 cb_model: 先照原样分成 N 簇, `refine_labels` 再 ① 声纹中心余弦 ≥ 0.78 的两簇并成一人
  ② 片段数占比 < 2% 的零碎簇按片段归到最像的大簇 ③ 编号按首次出现重排。不加载新模型, 不多花时间。transcript.json 记
  `diarization: {clusters_before, clusters_after}`。
- `smooth_short`: ≤ 4 个字的句子夹在同一个人的两句中间 (前后间隔都 < 2 秒) 归给他; 前后不是同一人的不动 (多半真是别人搭话)。
  CCRC 实测 305 句短句改了 20 句, 基本是「对不对?」「对吧?」这种自己带的尾巴。

**阈值怎么定的 (CCRC 实测声纹)**: 10 簇两两中心相似度是 0.5–0.8 连成一片, 没有明显断档; 只有一簇 (710 片段) 跟别的都 < 0.4 ——
多半是戴 AirPods 的那个人 (近讲), 其他人远场闷、声纹挤在一起。阈值 0.65–0.70 → 3 人, 0.75 → 6 人, 0.78 → 8 人, 0.85 → 不变。
轮廓系数最高的是 2 人 (近讲 vs 其他), 说明的是录音条件, 不是真人数。取 FunASR 自动模式自己的 0.78 (偏不并): 一个人拆成两个编号,
起同一个名字就并回来了; 两个人并成一个, 话和待办就记到一个人头上, 没法救。

**录音条件才是大头**: 一个人戴 AirPods 录 10 人的会, 别人的声音又远又闷, 声纹分不开、字也认不准。重要的会用笔记本自带麦克风或会议
全向麦放桌子中间; 线上会议勾「同时录对方的声音」(两条音轨天然分开)。

**老会议**: 说话人那一栏右边「重新转写」(一点就转, 收起时也在): 原转写 (含改过的错字) 另存 `transcript.before-<时间>.json`,
起过的名字挪成 `speakers.before-<时间>.json` (编号重新分了, 名字对不上), 纪要不动。

**顺手修的两个**: ① 转写进度原来只靠一次性事件, 界面重订阅的空当、切走再回来都会漏, 一直显示「准备中」—— 后端记当前阶段,
界面每 3 秒问一次 (`meeting_transcribe_phase`), 并显示已用时间。② 转写中 Companion 关了 / 重启了, meta 永远是「转写中」,
「重新转写」也不让点 —— 列表时这个进程里没在转写就收尾 (有结果算已转写, 没有算失败)。

## 11. 纪要质量: 模型、让小鲶改的提示词、偶发解析失败 (11/17, Companion 1.2.206)
