# 群里一起改文档 (各自改、系统合并) —— 详细设计

11/11 鸿波「协同的群聊, 现有文档的修改协同是不是不支持?」→「是不是有可能各自改完后, 由系统完成合并?」→ 出设计。

场景: 群里有人发一份现成的文档 (方案 / 合同 / 报价表 / 汇报 PPT), 请几位同事各自修改。每个人照常用自己的
Word / WPS / Excel / PowerPoint 在本机改, 改完交回; **发起人的鲶鱼**把大家的修改合成一版, 没冲突的自动合,
冲突的列出来让发起人定, 合好的新版本发回群里, 每一版都留底。

不做多人同屏实时编辑 —— 那是在线文档的事, 而且要求文档内容常驻中央, 跟我们的边界 (中央只转交) 冲突。

一句话流程: 发起人在群里点「请大家修改」→ 同事点「下载修改」→ 用本机软件改 → 点「交回」(只回给发起人)
→ 发起人本机三方合并 → 冲突逐条定 (小鲶给建议) → 群里出「v2 合并版」+ 修订痕迹。

## 1. 现有积木 (复用, 不重造)

| 积木 | 位置 | 本功能用法 |
|---|---|---|
| 群文件 | tool-bridge `colleague_rooms_files.py` (≤5MB 邮筒分块) / `colleague_rooms_bigfiles.py` (≤200MB 中央只存一份密文) | 原版、交回的修改稿、合并版都是普通群文件, 传输 / 加密 / 补块 / 7 天期限全部照旧 |
| 群里的卡片 + 状态 | `colleague_rooms_forms.py` (表卡 `form` + `form_status`)、`colleague_rooms_tasks.py` | 照这个做法加 `revise` 卡和 `revise_status` 状态 |
| 群消息发送 | `colleague_rooms._broadcast` (发给群里已加入的人, outbox 补发) | 加一个 `only=[...]` 参数: 交回稿只发给发起人 |
| Office 读写 | tool-bridge 已依赖 `python-docx` / `openpyxl` / `python-pptx`; `docx_export.py`、`forms_excel.py` | 三种格式的拆分、合并、写回 |
| 小鲶调大模型 | `gateway_llm.call_llm` | 冲突处给「兼顾双方」的建议稿 |
| 本机群聊库 | `colleague_rooms_store.py` (整库加密) | 文档版本链、交回记录、冲突决定都记这里 |
| 打开文件 | `roomFileSave` → `~/Downloads/鲶鱼群文件/<群名>/` | 「下载修改」落到同一个地方, 文件名带版本 |

## 2. 发起

1. 两个入口:
   - 群里某条消息的文件旁边多一个「请大家修改」(自己发的、别人发的都行 —— 谁点谁是发起人);
   - 输入框的「+」里「发文档请大家改」, 选本机文件; 或跟小鲶说「把这份方案发群里请王五和李四改, 周五前」。
2. 选: 请谁改 (群里已加入的人, 默认全部)、截止时间 (可空)、一句说明 (「重点看第三章报价」)。
3. 发出去 = 一条普通群消息, 带原文件 + 一张 `revise` 卡:

```json
{"rev_id": "r_20261111_ab12cd", "doc_id": "d_7f3e…", "title": "XX 项目实施方案", "version": 1,
 "file_id": "f_…", "sha256": "…", "fmt": "docx", "owner": "<发起人邮箱>",
 "editors": ["a@…", "b@…"], "deadline": "2026-11-14", "note": "重点看第三章报价"}
```

   - `doc_id`: 这份文档的身份, 整条版本链共用; `version`: 这一轮基于第几版。
   - `fmt` 决定能不能合 (§5); 合不了的格式卡上直接写「这种格式只能整份选用, 不能自动合并」。
4. 发起人本机记一份 **原版底稿** (base): `docs/<doc_id>/v1.<ext>` 存进群聊库, 不依赖群文件 7 天期限 ——
   合并永远要拿得到底稿。

## 3. 修改 (每位同事本机)

1. 卡片上三个按钮: **下载修改** / **不改了** (可写一句原因) / 看说明。
2. 「下载修改」把文件写到 `~/Downloads/鲶鱼群文件/<群名>/XX 项目实施方案 (v1·待我修改).docx` 并用默认程序打开。
   同时**在文件里埋一个记号**: docx / xlsx / pptx 写进自定义文档属性 `catfish_rev = r_…:v1` (Word、WPS、Excel、
   PowerPoint 另存都会保留); md / txt / csv 不埋, 靠本机记的路径认。
3. 群里那张卡上显示「王五在改」(发一条 `revise_status: editing`, 只有状态)。
4. 改完点卡上的「交回」: 默认就是刚才那个文件 (本机记了路径); 也可以选别的文件 / 直接把文件拖进群 ——
   拖进来的文件如果带 `catfish_rev` 记号, 输入框上方提示「这是《XX 项目实施方案》v1 的修改, 交回给张三?」。
5. 交回 = 发一条 `revise_return` 消息, **只发给发起人** (`only=[owner]`), 带修改稿文件; 同时给全群发
   `revise_status: returned` (只有「王五交回了」, 不带内容)。交回前在本机先算一遍跟 v1 的差异:
   - 一点没改 → 提示「跟原版一样, 还要交回吗?」, 交回就记成「看过, 没改」;
   - 格式变了打不开 / 不是同一份文档 (记号对不上、结构差太多) → 提示, 不让误交。
6. 截止前可以再交, **后交的覆盖先交的**; 截止后照样能交, 发起人那边标「逾期」。

## 4. 合并 (发起人本机)

### 4.1 什么时候合

- 卡片的进度: 每人一行 —— 在改 / 交回了 / 看过没改 / 不改了 / 没动静; 「催一下」给没交的人发 `revise_remind`。
- **全部交回 (或不改了) 后自动合一次**, 结果先只给发起人看; 发起人也可以随时点「先合已交的」。
- 合并只在发起人本机做: 输入 = 底稿 v1 + 每份交回稿, 输出 = 合并稿 + 一份合并报告。

### 4.2 怎么合 (N 份一起三方合并)

对每份交回稿, 先算出它**相对底稿改了哪些「单元」**(单元按格式定, 见 §5), 得到每个人的改动集合。然后:

| 情况 | 处理 |
|---|---|
| 某个单元只有一个人动了 | 直接用他的 |
| 几个人改成了一模一样 | 用这个, 报告里记「王五、李四都这么改」 |
| 几个人改得不一样 | **冲突**, 进 §4.3 |
| 一个人删了、另一个人改了 | 冲突 (不偷偷删) |
| 新增的单元 (插入段落 / 行 / 页) | 按它在底稿里的前后位置插回去; 两个人在同一处各插了东西, 都保留, 按交回先后排 |

不是两两依次合 (A+B 合完再合 C 会让 C 的改动跟「A+B 的结果」比, 冲突判错), 而是所有人都跟同一份底稿比。

### 4.3 冲突

合并面板里每个冲突一张卡:

```
第 3.2 节「报价」第 2 段
  原文:   实施周期 3 个月, 总价 48 万。
  王五:   实施周期 4 个月, 总价 48 万。
  李四:   实施周期 3 个月, 总价 52 万 (含培训)。
  小鲶建议: 实施周期 4 个月, 总价 52 万 (含培训)。   ← 说明: 两处改的是不同的数, 可以都要
  [用小鲶的] [用王五的] [用李四的] [保留原文] [我自己改]
```

- 小鲶建议走 `gateway_llm.call_llm`, 只送这个冲突单元的原文 + 各人改法 + 前后各一段上下文, 不送整份文档。
  提示词要求: 只在两人改的是不同内容时才合, 意思相反的不硬合 (那就不给建议, 只写「两人意见相反, 请你定」)。
  数字、金额、日期、人名在建议里出现的必须来自某个人的改法 (程序核对, 对不上就丢掉建议)。
- 默认什么都不选; **冲突没定完不能出合并版**。
- 「我自己改」: 一个文本框, 以小鲶建议或某人的版本为起点。

### 4.4 出合并版

1. 发起人点「发出合并版」: 生成 `v2`, 存进本机版本链, 发到群里 (普通群文件 + `revise_status: merged`
   + 一段报告「合并了王五 5 处、李四 3 处; 冲突 2 处已定」)。
2. **Word 合并版带修订痕迹**: 每处修改都是 Word 的修订 (`w:ins` / `w:del`), 修订作者 = 改的人的名字, 时间 = 交回时间;
   发起人自己定的冲突, 作者写发起人。打开就能看「谁改了哪里」, 可以在 Word 里逐条接受 / 拒绝。
   同时附一份「已全部接受」的干净版, 两份一起发 (文件名 `… v2 修订版.docx` / `… v2.docx`)。
3. Excel 合并版: 改过的单元格加批注「王五: 原值 48 → 52」, 另加一个「修改记录」工作表列出每处改动。
4. PPT 合并版: 被改过的页在备注里写「这页用的是李四的版本」。
5. 想接着改: 在 v2 上再点「请大家修改」, 就是新一轮 (底稿 = v2)。
6. **迟到的交回** (基于 v1, 但 v2 已经出了): 照样能合 —— 底稿用 v1, 跟 v2 做三方合并, 进下一版; 报告里标「迟到, 基于 v1」。

### 4.5 版本记录

群消息里每份合并版都带 `doc_id`; 群文件列表 (或文件旁「版本」) 打开一个面板:

```
XX 项目实施方案
  v3  11/18  张三合并 (王五、李四)          [打开] [跟上一版对比]
  v2  11/14  张三合并 (王五、李四、赵六)    [打开] [跟上一版对比]
  v1  11/11  张三发起
```

- 「对比」生成一份带修订痕迹的 docx (任意两版之间), 用 Word 打开看。
- 每份交回稿发起人本机都留着 (群聊库里), 群成员看到的是每一版合并稿; 交回稿只有发起人和交回的人自己有。

## 5. 各格式的「单元」和合并方式

| 格式 | 单元 | 怎么对齐 | 写回 | 合不细的地方 (行为) |
|---|---|---|---|---|
| md / txt / 知识库页面 | 段落 (空行分隔), 冲突时细到行 | 经典 diff3 (按段落序列 LCS) | 原文本 | 无 |
| csv | 行; 有表头时按单元格 | 有主键列按主键对齐, 没有按行内容 LCS | csv | 无 |
| xlsx | 单元格 (工作表 + 行键 + 列名) | 每张表: 认表头行, 找主键列 (唯一、非空的第一列, 如「编号」「项目部」); 有主键按主键对齐行, 没有按整行内容 LCS 对齐; 列按表头名对齐 | 在发起人选的「主版本」(默认底稿) 上改值, 保留原格式 / 公式 / 合并单元格 | 公式单元格: 比的是公式文本, 不比计算结果; 增删整张工作表按表名; 图表、数据透视表整张取底稿, 有人改了在报告里提示「图表没合, 请手动看」 |
| docx | 正文的块: 段落、表格单元格 (表格按行列); 页眉页脚各算一块 | 块序列按 (文字 + 样式名) 做 LCS 对齐; 对上了再在块内按词比 | 底稿的 XML 上逐块替换, 修改处写成修订; 块的格式用改的人那一版的 | 只改了格式 (文字没变) 的块: 一个人改格式、另一个人改文字 → 用改文字的, 报告里写「王五对这段的格式调整没合进来」; 图片、文本框、批注、脚注按块整体对待, 两人都改了就是冲突; 已有的修订痕迹先按「全部接受」再比 |
| pptx | 页 (slide); 页里不再拆 | 按 PowerPoint 的页编号 (`sldId`, 改动、挪动后不变) 对齐; 删页、插页、调顺序都认 | 在底稿上替换 / 增删页 | 两人改了同一页 = 冲突, 整页二选一 (预览图并排给发起人看) |
| pdf / 图片 / 其它 | 整个文件 | — | — | 合并面板只给「用谁的版本」 |

- 老格式 `.doc / .xls / .ppt`: 发起时提示「先另存为 docx / xlsx / pptx 再发, 才能自动合并」, 不另存也能发, 按整份选用。
- WPS 存出的 docx / xlsx / pptx 就是标准格式, 照常合。
- 每次合并后用 python-docx / openpyxl / python-pptx 重新打开一遍合并稿做自检, 打不开就不出这一版, 报错给发起人。

## 6. 小鲶能做的

新工具 `catfish_revise` (一个工具多 action, 照 `catfish_form`): `start` / `status` / `merge` / `conflicts` / `resolve` / `versions` / `diff`。

- 员工可以说: 「把方案发群里请王五、李四改, 周五前」「谁还没交」「把大家改的合一下」「冲突里报价那条用李四的」
  「v2 和 v1 比改了哪些」「把 v3 发给客户前给我总结一下这轮改了什么」。
- 发起 / 催 / 发出合并版要先念给员工、带 confirmed 才做 (跟 `catfish_form` 同一条规矩); 交回只有员工自己在卡上点。
- 冲突的「定」小鲶可以代点, 但发出合并版前员工看一遍合并报告。

## 7. 数据边界

- 中央只看到密文群消息和密文文件 (跟现在群里发文件完全一样), 不新开中央接口, 不新增中央存储。
- 交回稿只发给发起人, 其他群成员看不到别人的修改稿, 只看到合并版。
- 小鲶建议: 只把冲突那一小段送给大模型 (走公司自己的 LLM 网关, 跟平时对话同一条路), 不送整份文档。
- 文档里埋的 `catfish_rev` 记号只有编号, 不含姓名 / 邮箱; 文件发给外部 (客户) 前, 「发出合并版」生成的干净版不带这个记号。

## 9. 实现顺序

1. `doc_merge` 的文本 / csv / xlsx (单元最清楚, 先把 N 份三方合并和冲突模型做扎实), 单测覆盖 §4.2 每一种情况。
2. docx (对齐 + 修订痕迹写回), pptx (按页)。
3. 群里的卡片、交回、版本链、合并面板、小鲶工具。
4. 端到端: 两个测试账号 + 临时 gateway (跟填表那次一样)。

## 10. 验收

1. 一份虚构的 20 页实施方案 docx, 三个人各改: A 改第 2 章两段、B 改报价表两个单元格、C 改了 A 也改的一段 →
   自动合并 4 处、冲突 1 处; 合并版在 **Microsoft Word 和 WPS** 里打开, 修订作者对、可逐条接受 / 拒绝, 全部接受后跟干净版一致。
2. 虚构报价 xlsx: 两人改不同单元格、一人插行、一人删行 → 按主键对齐正确; 公式、格式、合并单元格保留。
3. pptx: 两人改不同页 + 一人挪了页顺序 → 合并正确; 同一页冲突给出两张预览。
4. md / 知识库页面: diff3 结果跟 `git merge-file` 一致 (用它当对照)。
5. 一点没改的交回、迟到的交回 (v2 已出)、交错文件 (记号对不上) 各走一遍。
6. 小鲶建议: 冲突里的数字 / 日期必须来自某个人的改法; 意思相反的不给建议。
7. 老版 Companion 收到卡、改完当普通文件发回 → 新版发起人认成交回。
8. 中央库 / 日志里搜不到任何文档内容 (跟群文件现有测试一样)。
9. Mac + Windows 各走一遍。

## 11. 已确认 (11/11 鸿波「按建议定」)

1. 交回稿只有发起人 (和交回的人自己) 有, 群里只看到合并版和「谁交了」。
2. 只有发起人能合并。
3. 合并分析由发起人打开合并面板时跑, 不自动发; 看过冲突再点「发出合并版」。

- 各软件存盘会改大量跟内容无关的写法 (rsid、run 怎么拆、默认格式显式写出、页眉部件改名、PPT 页编号重排)。
  LibreOffice 原样另存一份交回, Word / PPT 都判成「看过没改」(测试里钉住)。
- Word 比的是: 文字 + 段落样式 (按样式名) + 对齐 / 列表级别 + **实际生效的**字符格式 (加粗 / 斜体 / 下划线 / 删除线 / 颜色 /
  字号 / 上下标 / 大小写, 顺着文档默认 → 样式链 → 直接格式算) + 图片等对象的内容哈希。
  **只改了字体名、段落间距 / 缩进、表格边框列宽的段落不算改动, 不合进来** (段落有别的修改时整段用改的人的版本, 这些格式会一起带过来)。
- PPT 比每页的形状: 类型、位置尺寸 (取整到约 1mm)、文字和实际生效的字符格式、图片 / 图表内容、表格、版式名、备注。
  **只改了形状填充 / 线条 / 阴影、段落对齐行距、字体名、背景、切换动画的页不算改动**。页编号被另存重排时改按内容认页。
- Excel 按单元格比值和公式 (公式先换回底稿坐标, 插行不会被当成改了公式); 「只改了格式」的提醒按实际生效的格式比
  (加粗 / 斜体 / 下划线 / 删除线 / 字号 / 颜色 / 填充 / 数字格式 / 对齐 / 有无边框; 显式写出的默认值、主题色和 RGB 两种写法都算一样)。
  openpyxl 存一遍会丢的东西 (形状文本框、迷你图、数据条等) 合并版里不带, 警告里逐条写出, 不静默丢。
- 页眉页脚按「第几节 · 默认 / 首页 / 偶数页」对上, 不按部件名; 脚注尾注按编号。
- 冲突时 PPT 给发起人看的是各版本这页的文字 (客户机上没有能把页渲染成图片的东西), 不是预览图。
