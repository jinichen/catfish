# 小鲶手机端设计（不依赖微信 / 飞书）

> 状态：第一期已实现（中转站 + Companion 手机通道 + 网页 `/m`）· 设计稿第二版，§11 五项定稿，部署分开发 / 正式两套（§8）· 2026-11-01
> 实现与设计稿的差别见 §12。
> 起因：鸿波——「小鲶要怎么样才能有自己的 App 或小程序，而不是完全依靠微信、飞书等？」
> 参照：Hermes 生态的手机 App（Hermex、hermesapp.dev、Onepilot 等，均为第三方）都是同一个思路——
> **手机只是遥控器，agent 跑在用户自己的电脑 / 服务器上**。iOS 不允许 App 常驻后台跑任意程序，
> agent 本身没法跑在手机上。

## 1. 目标与不做的事

**要做**
- 员工在手机上跟**自己电脑上的小鲶**对话（流式回复、语音输入）。
- 手机上处理**审批**：小鲶要做敏感操作时，在手机上点同意 / 拒绝。
- 手机上看**早安简报**、收**任务完成**通知。
- 数据边界不变：内容只在员工电脑上，中央不存、看不到明文。

**不做**
- 不在手机上跑 agent、不在手机上存员工的记忆 / 知识库 / 邮件。
- 不做「中央托管的小鲶」（那是另一种产品，违反数据边界）。
- 第一期不做原生推送（见 §7 分期）。

## 2. 架构

```
手机 (网页版 / 原生壳)
   │  ① 单位账号登录 (OIDC, 跟门户同一套)
   │  ② 端到端加密的消息 (中央看到的只是密文)
   ▼
中央「中转站」 relay  ── 只转发、不存内容、不排队；只记元数据
   ▲
   │  ③ 电脑主动连上来 (WebSocket 长连接, 不用对外开端口, 内网 / NAT 后都行)
Companion「手机通道」
   │  ④ 只放行白名单里的几种请求
   ▼
本机小鲶 Hermes API (127.0.0.1:8642) / Companion 本地数据 (早安简报)
```

- **电脑不在线**（关机 / 休眠 / 断网）：中转站立即告诉手机「电脑不在线」，不替它存消息。
- **一个人多台电脑**：手机上选连哪台（按配对时起的名字区分）。
- **现有微信接入不动**：自己的 App 是新增的一条路，微信 / 飞书继续可用。

## 3. 数据边界：跟「同事邮筒」同一个例外，而且更严

`CENTRAL-EDGE-DATA-BOUNDARY.md` 已有「中央只转交、不留存」的例外（同事邮筒，四条条件）。中转站照这四条做，还更严：

| 邮筒的条件 | 中转站 |
|---|---|
| payload 不透明，中央不解析、不写日志 | payload 是**端到端加密的密文**，中央连解析的能力都没有；静态测试拦住任何把帧内容写日志的代码（同 `test_central_log_no_content.py`） |
| 取走即清空，到期清空 | **根本不落盘、不排队**：收到一帧立刻转给另一端，另一端不在线就丢弃并回「不在线」 |
| 只留元数据，30 天删 | 只留：哪个员工、哪台手机 / 电脑、连接起止时间、转发了多少字节；30 天删 |
| 员工主动发起 | 每一条都是员工在手机上主动发的；电脑这边只回应，不主动往手机推内容（推送只推「有一个待审批」这类无内容提醒，见 §6） |

在员工电脑上，经中转站发给手机的回复记进「数据外发记录」：目的地记「手机（经中央中转，已加密）」，记大小、不存内容。外发记录里本来就能看到「往外发了什么」，这一条不能漏。

## 4. 配对与加密

**配对**（一台手机一次，不用摄像头）
1. 手机用单位账号登录，生成自己的密钥对，把公钥经中转站发给本人名下在线的电脑。
2. Companion 弹出「有一台新手机请求连接：iPhone · 验证码 025159」；手机上同时显示同样的 6 位数。
3. 员工在电脑上核对一致、点「允许」，Companion 回自己的公钥，配对完成。
4. 中央只知道「这个人配了一台手机」（元数据），不经手私钥。

**加密**
- 双方用 NaCl box（X25519 + XSalsa20-Poly1305）。Rust 用 `crypto_box` crate，网页用 `tweetnacl`，两边都是成熟实现。
- 每条消息带递增序号，防重放；每次连上换临时会话密钥，旧消息事后解不开。
- 手机丢了：在 Companion「设置 → 手机」里撤销那台手机，它的公钥立即作废。

**登录**：中转站只认单位身份令牌（identity-server 签发），手机和电脑必须是**同一个人**才能配对、互通。

## 5. Companion「手机通道」放行什么

只放行白名单，手机拿不到电脑上的任意能力：

| 请求 | 转给谁 | 说明 |
|---|---|---|
| 发消息（流式） | Hermes `POST /v1/chat/completions` | 跟 Companion 自己对话走同一条路；用单独的会话，Companion 的会话列表里也看得到 |
| 审批 | Hermes `POST /v1/sessions/{sid}/approval` | 流里的 `approval.request` 事件原样转给手机 |
| 会话列表 / 历史 | Hermes 会话接口（只读） | |
| 早安简报 | Companion 本地数据（只读） | |
| 心跳 | — | |

**不放行**：读写文件、改配置、装技能 / MCP、看外发记录明细、换机迁移等。

**审批的规矩**：沿用现有审批设计（只读免批、删除类每次问）。手机上**只能单次批准**，跟微信一样不能「始终允许」。「始终允许」只能在电脑上点，因为手机更容易被别人拿到。

## 6. 推送（第二期）

- 推送内容**不带正文**，只有「你有一个待审批」「任务完成了」，点开后通过加密通道拉具体内容。
- iOS 走苹果推送（APNs）。安卓在国内要接各厂商推送（华为、小米、OPPO、vivo），或用第三方聚合服务。第三方聚合会经过别人的服务器，即使不带正文也要在客户 IT 那里说清楚。

## 7. 手机端形态与分期

| 期 | 形态 | 内容 | 粗估 |
|---|---|---|---|
| 一 | **网页版**（中央门户下的 `/m`，可「添加到主屏幕」） | 对话、审批、早安简报；单位账号登录；配对 | 中转站 1 周 + Companion 手机通道和配对 1.5–2 周 + 网页 1.5 周 |
| 一点五 | 把网页版挂进**企业微信 / 飞书的工作台应用** | 员工从熟悉的入口打开；数据直接走中转站，不经它们的聊天服务器 | 2–3 天 |
| 二 | **原生 App 外壳**（Capacitor 或 Tauri Mobile） | 推送、私钥进系统钥匙串、语音体验 | 2–3 周 |

**微信小程序**：要公网域名 + ICP 备案 + 微信审核，而多数客户的中央在内网，手机在外面连不上——不作为主渠道；客户中央能上公网的可以后加。

**iOS 分发**：企业内部用 Apple Business Manager + MDM 下发，或 TestFlight；不上公开 App Store 也能用。

## 8. 部署：开发环境和正式环境

**共同原则：代码里不写死任何地址。**
- 中转站就是中央网关里的一个路由（`/relay/ws`），不是新进程、不占新端口。
- Companion 连中转站的地址**由它已配好的中央地址推出来**：`http://…` 对应 `ws://…/relay/ws`，`https://…` 对应 `wss://…/relay/ws`。中央地址填什么，中转站就跟着走什么。
- 手机网页 `/m` 跟门户同源，接口地址用相对路径，不单独配。
- 配对只认「同一个单位账号」和验证码，**跟 IP 无关**。电脑换了 IP、重连之后，配对照样有效。

### 8.1 开发环境（开发 Mac，IP 会变，一律 127.0.0.1）

| 组件 | 地址 | 说明 |
|---|---|---|
| 中央网关 + 中转站 | `127.0.0.1:8999` | launchd `com.catfish.gateway`，改完中央代码 kickstart 一次 |
| identity-server | `127.0.0.1:8998` | OIDC issuer 就是这个地址；令牌里的地址跟它一致 |
| 门户 + 手机网页 `/m` | `127.0.0.1:5173` | vite 开发服务器 |
| Companion 手机通道 | 连 `ws://127.0.0.1:8999/relay/ws` | 自动由中央地址推出，不用另配 |
| 本机小鲶 Hermes | `127.0.0.1:8642` | 不变 |

开发时「手机」这一头怎么测（都不依赖固定 IP）：
1. **日常**：桌面浏览器打开 `http://127.0.0.1:5173/m`，开手机模拟（Chrome 设备模式）。开发主要靠这个，配对、对话、审批全链路都能测。
2. **看真实手机外观**：iOS 模拟器里的 Safari 能直接访问本机 `127.0.0.1`，不用转发。
3. **偶尔上真机**：真手机访问不到电脑的 127.0.0.1。需要时临时开一个隧道（如 `cloudflared tunnel --url http://127.0.0.1:5173`，拿到临时 https 网址），测完就关。开发配置不因此改动，中央仍监听 127.0.0.1。
   - 这条要注意：隧道的临时网址跟 identity 的 issuer（127.0.0.1:8998）不一致，登录回调会被拒。所以真机测试时只测「已登录后」的页面，或者给 identity 临时加一个允许的回调地址。这个开发辅助开关只在开发环境的 `.env` 里，正式环境没有。
4. **自动化测试**：中转站用 pytest 起内存里的两个 WebSocket 客户端互相转发，不需要网络地址。Companion 侧用本地假中转站。

单机演示 / 试用（客户那边一台电脑装全套）沿用安装脚本的 `LOCAL_ONLY=1` 单机模式，地址同样是 127.0.0.1。这种情况只能用桌面浏览器开 `/m` 演示，真手机连不上，文档里写明。

### 8.2 正式环境（客户服务器）

**默认：中转站跟中央一起部署**（同一个网关进程、同一个 HTTPS 域名 / 证书），安装包不多一个服务。

| 项 | 要求 |
|---|---|
| 地址 | 用安装时填的中央地址（固定 IP 或域名），从 `.env` 读，不写死 |
| HTTPS | 必须。手机浏览器只在 https 下给麦克风（语音输入）、「添加到主屏幕」也要 https |
| 员工电脑 → 中转站 | 内网直连，电脑主动连出，不用对外开端口 |
| 手机 → 中转站 | 在公司内网（Wi-Fi）直接可用。在公司外面，有两种办法，由客户 IT 选：① 员工手机连 VPN；② 把中央的 `/relay/ws` 和 `/m` 两个路径经反向代理开放到公网，其余路径不开放 |
| 限速 | 每人连接数上限、每连接流量上限、配对请求频率上限（防暴力猜验证码） |
| 手机数量 | 每人最多配几台手机可以设置：`.env` 里 `CATFISH_MOBILE_MAX_DEVICES`，默认 3；设成 0 就是不开放手机端。改完重启网关生效。已经配好的手机超过新上限时不会被踢掉，只是不能再加新的 |
| 元数据保留 | 连接记录 30 天删，跟同事邮筒同一个定时清理任务 |

**可选：中转站单独放 DMZ**（客户 IT 不愿意把中央任何路径开到公网时）
- 同一个网关镜像，用 `CATFISH_ROLE=relay` 只启动中转路由 + 设备登记表，不带其他接口。
- 它只需要两样：向内网 identity-server 取公钥校验令牌、一张设备登记表（元数据）。不碰模型、不碰用户数据。
- 员工电脑从内网连 DMZ 的中转站；手机从外网连。中央本体继续只在内网。
- 安装脚本加一个选项生成这份配置，INSTALL.md 加一节。不是默认路径，客户提出再交付。

### 8.3 上线检查

- 开发环境跑通：桌面浏览器 `/m` ↔ Companion，配对、对话、审批、早安都走通；数据外发记录里有「手机（经中央中转，已加密）」。
- 正式环境：用 https 地址在真手机上走通一遍（内网 Wi-Fi + 外网 VPN 或公网各一次）；抓包确认中转站经手的都是密文；中转站日志里没有帧内容。

## 10. 顺带：飞书 / 企微「公司共用一个机器人」

现状：Hermes 自带飞书、企业微信（还有钉钉）接入，但员工的小鲶各在自己电脑上，一个机器人应用在长连接模式下
消息只推给其中一个客户端，分不到各人电脑上 —— 所以要每人建一个机器人应用，管理员负担重。

有了中转站以后：

```
员工在飞书 / 企微里 @机器人 ──> 中央「中转站」(公司唯一的机器人在这里收消息)
                                   │ 按发消息的人 (飞书 open_id / 企微 userid ↔ 单位账号) 找到他本人的电脑
                                   ▼
                              员工电脑上的 Companion 手机通道 ──> 本机小鲶 ──> 回复原路回到飞书 / 企微
```

**数据边界（鸿波 2026-11-01 拍板）**：飞书 / 企微送来的消息是明文，但它本来就经过了飞书 / 腾讯的服务器，
属于员工已经愿意交给这些平台的内容；中转站只转、不存，**不算违反数据边界**。照以下条件做：
- 中转站不落盘、不排队、不写日志（同 §3），员工电脑不在线就直接回「电脑不在线」；
- 中央只留元数据（谁、哪个平台、时间、字节数），30 天删；
- 账号对应关系（飞书 open_id / 企微 userid ↔ 单位账号）来自通讯录同步，是元数据；
- 员工本人在 Companion 里打开「允许从飞书 / 企微找我」才转，默认关。

好处：管理员只建一个机器人；员工不用自己建；消息格式限制照旧（手机上短回复、审批回 1 / 2）。
跟手机网页版 / App 共用同一套中转站和电脑端手机通道，多做的只是中央这边的飞书 / 企微收发适配（约 1 周）。

## 12. 实现记录（2026-11-01 第一期）

| 位置 | 文件 |
|---|---|
| 中央中转站 | `central/llm-gateway/src/catfish_gateway/relay_router.py`（入口 + 登录帧）、`relay_hub.py`（转发、限速、配对关系）、`relay_db.py`（元数据表 / 无库时进程内存）、`relay_app.py`（DMZ 只中转模式）、alembic `20261101_017` |
| Companion | `src-tauri/src/commands/mobile_bridge/`（`crypto.rs` 加密与分段、`store.rs` 本机存储、`ops.rs` 白名单、`mod.rs` 连接与配对）；界面 `tabs/Dashboard/MobileCard.tsx`、`components/MobilePairDialog.tsx` |
| 手机网页 | `central/web/src/mobile/`（`crypto.ts` / `client.ts` / `MobileApp.tsx` / `pwa.ts`）、`public/m-manifest.webmanifest` |
| 交付 | `docker-compose*.yml` 的 `CATFISH_MOBILE_MAX_DEVICES`、`catfish-locations.conf` 的 `/relay/`、`docker-compose.relay.yml` + `relay-dmz/`、INSTALL.md「手机访问」 |

跟设计稿不一样的地方：
- **验证码 6 位**（设计稿写 4 位）：中转站被冒充时撞对的机会从万分之一降到百万分之一，员工多看两位数。
- **网关多进程**：生产网关默认 4 个进程，手机和电脑可能连在不同进程上。对方不在本进程时经 PostgreSQL NOTIFY 交过去（即时通知，没人收就没了，不入表）。NOTIFY 单条上限 8000 字节，所以密文字段限 6000 字符，大消息由两端拆成 4000 字节一段。
- **令牌不放网址里**：浏览器的 WebSocket 不能带 Authorization 头，令牌放在连上后的第一帧里（放网址会进反向代理的访问日志）。令牌到期中转站断开，两端用新令牌重连。
- **对话走 `catfish_source=companion-chat`**：跟电脑上聊天同一个来源标记，记忆照常生效（新开一个来源会被记忆闸当成后台任务跳过）。手机上的对话写进同一个对话列表，电脑上也看得到。
- **手机页不调 `/api/me`**：DMZ 方案里对外只开 `/m`、登录页和 `/relay/`。
- **外网登录的约束**（写进 INSTALL.md）：手机在外网登录时，OIDC issuer 必须是外网能打开的那个 https 域名，内网电脑用同一个域名。
- **必须 https**：手机浏览器只在安全连接下提供算验证码要用的加密接口；http 打开会直接提示。开发环境的 `127.0.0.1` 算安全连接。
- **语音输入**：第一期用手机输入法自带的语音输入，不另做。
