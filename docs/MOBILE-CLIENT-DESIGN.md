# 小鲶手机端设计（不依赖微信 / 飞书）

> 状态：设计稿，待评审 · 2026-11-01
> 起因：鸿波——「小鲶要怎么样才能有自己的 App 或小程序，而不是完全依靠微信、飞书等？」
> 参照：Hermes 生态的手机 App（Hermex、hermesapp.dev、Onepilot 等，均为第三方）都是同一个思路——
> **手机只是遥控器，agent 跑在用户自己的电脑 / 服务器上**。iOS 不允许 App 常驻后台跑任意程序，
> agent 本身没法跑在手机上。

## 1. 目标与不做的事

**要做**
- 员工在手机上跟**自己电脑上的小鲶**对话（流式回复、语音输入）。
- 手机上处理**审批**：小鲶要做敏感操作时，在手机上点同意 / 拒绝。
- 手机上看**早安简报**、收**任务完成**通知。
- 数据边界不变：内容只在员工电脑上，中央不存、看不到明文。

**不做**
- 不在手机上跑 agent、不在手机上存员工的记忆 / 知识库 / 邮件。
- 不做「中央托管的小鲶」（那是另一种产品，违反数据边界）。
- 第一期不做原生推送（见 §7 分期）。

## 2. 架构

```
手机 (网页版 / 原生壳)
   │  ① 单位账号登录 (OIDC, 跟门户同一套)
   │  ② 端到端加密的消息 (中央看到的只是密文)
   ▼
中央「中转站」 relay  ── 只转发、不存内容、不排队；只记元数据
   ▲
   │  ③ 电脑主动连上来 (WebSocket 长连接, 不用对外开端口, 内网 / NAT 后都行)
Companion「手机通道」
   │  ④ 只放行白名单里的几种请求
   ▼
本机小鲶 Hermes API (127.0.0.1:8642) / Companion 本地数据 (早安简报)
```

- **电脑不在线**（关机 / 休眠 / 断网）：中转站立即告诉手机「电脑不在线」，不替它存消息。
- **一个人多台电脑**：手机上选连哪台（按配对时起的名字区分）。
- **现有微信接入不动**：自己的 App 是新增的一条路，微信 / 飞书继续可用。

## 3. 数据边界：跟「同事邮筒」同一个例外，而且更严

`CENTRAL-EDGE-DATA-BOUNDARY.md` 已有「中央只转交、不留存」的例外（同事邮筒，四条条件）。中转站照这四条做，还更严：

| 邮筒的条件 | 中转站 |
|---|---|
| payload 不透明，中央不解析、不写日志 | payload 是**端到端加密的密文**，中央连解析的能力都没有；静态测试拦住任何把帧内容写日志的代码（同 `test_central_log_no_content.py`） |
| 取走即清空，到期清空 | **根本不落盘、不排队**：收到一帧立刻转给另一端，另一端不在线就丢弃并回「不在线」 |
| 只留元数据，30 天删 | 只留：哪个员工、哪台手机 / 电脑、连接起止时间、转发了多少字节；30 天删 |
| 员工主动发起 | 每一条都是员工在手机上主动发的；电脑这边只回应，不主动往手机推内容（推送只推「有一个待审批」这类无内容提醒，见 §6） |

在员工电脑上，经中转站发给手机的回复记进「数据外发记录」：目的地记「手机（经中央中转，已加密）」，记大小、不存内容。外发记录里本来就能看到「往外发了什么」，这一条不能漏。

## 4. 配对与加密

**配对**（一台手机一次，不用摄像头）
1. 手机用单位账号登录，生成自己的密钥对，把公钥经中转站发给本人名下在线的电脑。
2. Companion 弹出「有一台新手机请求连接：iPhone · 验证码 4821」；手机上同时显示 4821。
3. 员工在电脑上核对一致、点「允许」，Companion 回自己的公钥，配对完成。
4. 中央只知道「这个人配了一台手机」（元数据），不经手私钥。

**加密**
- 双方用 NaCl box（X25519 + XSalsa20-Poly1305）。Rust 用 `crypto_box` crate，网页用 `tweetnacl`，两边都是成熟实现。
- 每条消息带递增序号，防重放；每次连上换临时会话密钥，旧消息事后解不开。
- 手机丢了：在 Companion「设置 → 手机」里撤销那台手机，它的公钥立即作废。

**登录**：中转站只认单位身份令牌（identity-server 签发），手机和电脑必须是**同一个人**才能配对、互通。

## 5. Companion「手机通道」放行什么

只放行白名单，手机拿不到电脑上的任意能力：

| 请求 | 转给谁 | 说明 |
|---|---|---|
| 发消息（流式） | Hermes `POST /v1/chat/completions` | 跟 Companion 自己对话走同一条路；用单独的会话，Companion 的会话列表里也看得到 |
| 审批 | Hermes `POST /v1/sessions/{sid}/approval` | 流里的 `approval.request` 事件原样转给手机 |
| 会话列表 / 历史 | Hermes 会话接口（只读） | |
| 早安简报 | Companion 本地数据（只读） | |
| 心跳 | — | |

**不放行**：读写文件、改配置、装技能 / MCP、看外发记录明细、换机迁移等。

**审批的规矩**：沿用现有审批设计（只读免批、删除类每次问）。手机上**只能单次批准**，跟微信一样不能「始终允许」。「始终允许」只能在电脑上点，因为手机更容易被别人拿到。

## 6. 推送（第二期）

- 推送内容**不带正文**，只有「你有一个待审批」「任务完成了」，点开后通过加密通道拉具体内容。
- iOS 走苹果推送（APNs）。安卓在国内要接各厂商推送（华为、小米、OPPO、vivo），或用第三方聚合服务。第三方聚合会经过别人的服务器，即使不带正文也要在客户 IT 那里说清楚。

## 7. 手机端形态与分期

| 期 | 形态 | 内容 | 粗估 |
|---|---|---|---|
| 一 | **网页版**（中央门户下的 `/m`，可「添加到主屏幕」） | 对话、审批、早安简报；单位账号登录；配对 | 中转站 1 周 + Companion 手机通道和配对 1.5–2 周 + 网页 1.5 周 |
| 一点五 | 把网页版挂进**企业微信 / 飞书的工作台应用** | 员工从熟悉的入口打开；数据直接走中转站，不经它们的聊天服务器 | 2–3 天 |
| 二 | **原生 App 外壳**（Capacitor 或 Tauri Mobile） | 推送、私钥进系统钥匙串、语音体验 | 2–3 周 |

**微信小程序**：要公网域名 + ICP 备案 + 微信审核，而多数客户的中央在内网，手机在外面连不上——不作为主渠道；客户中央能上公网的可以后加。

**iOS 分发**：企业内部用 Apple Business Manager + MDM 下发，或 TestFlight；不上公开 App Store 也能用。

## 8. 部署：手机在公司外面怎么连

- 中转站必须从外网能访问（或员工连着 VPN）。
- 中转站**不存内容、只转发密文**，可以**单独部署在 DMZ**，不用把整个中央暴露到公网，比较容易过客户 IT 的审批。它只需要：校验身份令牌（向 identity-server 取公钥）、一张设备登记表（元数据）。
- 必须 HTTPS，加连接数和流量限速。

## 9. 要改的地方

| 位置 | 改什么 |
|---|---|
| 中央 `llm-gateway` | 新增 `relay_router.py`（WebSocket 中转）、`relay_db.py`（设备登记 + 连接元数据，alembic 新表）、日志静态测试；数据边界文档加「手机中转」一节 |
| 中央 `web` | `/m` 手机网页（对话、审批、早安、配对），PWA 清单 |
| Companion Rust | `mobile_bridge/`：连中转站、配对、加解密、白名单分发、外发记录记账；`device_migration/catalog.rs` 里登记新文件（配对密钥归「凭证」，换机不带，新电脑重新配对） |
| Companion 前端 | 「设置 → 手机」：配对确认、已配手机列表、撤销 |
| Hermes 插件 | 不用改（手机的请求在电脑上就是普通的 Hermes API 调用，身份、审批、外发记录照常生效） |

## 10. 顺带：飞书 / 企微「公司共用一个机器人」

现状：Hermes 自带飞书、企业微信（还有钉钉）接入，但员工的小鲶各在自己电脑上，一个机器人应用在长连接模式下
消息只推给其中一个客户端，分不到各人电脑上 —— 所以要每人建一个机器人应用，管理员负担重。

有了中转站以后：

```
员工在飞书 / 企微里 @机器人 ──> 中央「中转站」(公司唯一的机器人在这里收消息)
                                   │ 按发消息的人 (飞书 open_id / 企微 userid ↔ 单位账号) 找到他本人的电脑
                                   ▼
                              员工电脑上的 Companion 手机通道 ──> 本机小鲶 ──> 回复原路回到飞书 / 企微
```

**数据边界（鸿波 2026-11-01 拍板）**：飞书 / 企微送来的消息是明文，但它本来就经过了飞书 / 腾讯的服务器，
属于员工已经愿意交给这些平台的内容；中转站只转、不存，**不算违反数据边界**。照以下条件做：
- 中转站不落盘、不排队、不写日志（同 §3），员工电脑不在线就直接回「电脑不在线」；
- 中央只留元数据（谁、哪个平台、时间、字节数），30 天删；
- 账号对应关系（飞书 open_id / 企微 userid ↔ 单位账号）来自通讯录同步，是元数据；
- 员工本人在 Companion 里打开「允许从飞书 / 企微找我」才转，默认关。

好处：管理员只建一个机器人；员工不用自己建；消息格式限制照旧（手机上短回复、审批回 1 / 2）。
跟手机网页版 / App 共用同一套中转站和电脑端手机通道，多做的只是中央这边的飞书 / 企微收发适配（约 1 周）。
