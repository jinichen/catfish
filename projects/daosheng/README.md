## 二 · 不可回退的决定

> 这七条是十七轮调整的沉淀。修改前请先确认新需求是否真的推翻了它们。

### 1. AI Native 骨架，不是「传统系统 + AI 功能」

```
交互层        自然语言 · 现场多模态输入 · 主动推送
Agent 编排层   意图理解 → 任务分解 → 调用能力 → 人在回路 → 交付   ← 中心
能力与知识层   自部署模型 · 工具 · 技能 · 知识与记忆
数据语义层     统一语义模型 · 多形态存储 · 数据服务与权限
接入层        设备数据（集成商）· 既有系统 · 文档与外部数据
```

**论证（P2）**：这家企业的核心资产是隐性知识（配方经验、老师傅调参手感、认证踩坑经验、
品牌客户对接经验），传统信息化要求人先把知识填成表单才能管理，但人不愿填也填不完整；
而园区模式要求经验能规模化输出，否则「链主赋能」不成立。AI Native 把这件事反过来 ——
**人照常工作，系统从过程中提取知识；下游用自然语言调用，不必学系统。**

### 2. 四个 Agent，不是功能模块

| Agent | 页 | 关键立意 |
|---|---|---|
| 研发 Agent | P7 | 不要求研发改记录习惯，从他们本来在做的事里提取知识 |
| 生产 Agent | P8 | 不是让人查报表，而是持续观察 → 归因 → 建议 |
| 合规与客户 Agent | P9 | 认证与客户要求本质是「读文件、比对、组材料」 |
| 园区 Agent | P10 | ★ 把**能力**而非账号开放给下游 —— 赋能规模化的载体 |

### 3. 交付边界在「数据接入层」切一刀

```
交互与 Agent 层  ┐
能力与知识层     ├─ 本方案范围
数据语义层       ┘
────────────────────────────────
数据接入层       ★ 本方定规范，集成商实现，双方联调
边缘与设备层     设备供应商 + 系统集成商 + 在线检测仪表供应商
```

**现场零部署** —— 车间侧（OT）不部署任何本方推理组件，检测与视觉推理均由仪表厂商成套交付。

**但接口规范必须由本方定义。** 规范一并交出去的结果是「数据接进来了但不能用」——
点位缺失、频率不足、时间戳不同步，返工代价仍由上层承担。
**边界是「不实施」不是「不介入」。**

> **★ 2026-08-06 补：边缘网关 = OT 侧的 MCP Server**（鸿波提出）
>
> 上面这一刀原本散在三处陈述里（不做什么 / 参与方 / 基础设施），读者要自己拼。
> 收敛成一条原则：**平台不直连任何设备，边缘网关是唯一接口，对上以 MCP 暴露能力。**
>
> 不只是比喻 —— 平台的工具接入本来就走 MCP（`edge/tool-bridge/` 已同时实现
> `mcp_client.py` 与 `mcp_server.py`）。网关就是一个跑在 OT/IT 交界、
> 上行说 MCP、下行说工业协议的 server：
>
> | MCP 概念 | 网关上对应 | 谁定义 / 谁实现 |
> |---|---|---|
> | Resource | 工艺点位、批次记录、检测结果（只读订阅） | 能力中心 / 我方 |
> | Tool | 配方参数下发、开机准备度检查（调用留痕） | 能力中心 / 我方 |
> | Schema | 点位表 + 控制接口规范 | 能力中心 / —— |
> | 底层协议 | PLC 寄存器、OPC UA 节点、仪表串口 | —— / 系统集成商 |
>
> **类比必须在三处断掉**（写进 P7）：
>
> 1. **网关不是安全装置** —— 上下限硬约束在 PLC 侧组态。MCP server 做入参校验，
>    真正的拦截在下游；网关崩溃、被绕过或断网时，约束仍成立。
> 2. **网关不进实时回路** —— 毫秒级闭环与安全联锁归 PLC。网关上的写是批次级设定。
> 3. **网关故障不停线** —— 读路径旁路，写路径降级，产线按 PLC 现有设定继续跑。
>
> **副作用：「边缘常驻」这个说法缩水了。** 原来写成架构级新增，
> 现在看不必把 Agent 运行时搬进车间 —— 要补的是网关侧 Server 与平台侧的
> **远端 MCP 传输**（当前 `mcp_client.py` 只支持本机 stdio 拉子进程，
> 跨网段需 HTTP / SSE）。范围窄得多，仍属底座定向开发项。

### 4. 检测数据交专业厂商采集，我方做归因

厂商交付仪表与推理硬件；本方接**检测结果**，
做「产品性能 ↔ 工艺参数 ↔ 原料特性」的关联归因 ——
**「这批性能不达标是哪个参数导致的」没人做，且只有拿到全量数据才做得了。**

> **⚠ 2026-08-06 修正：原文写的是「视觉质检…缺陷 ↔ 工艺参数」，输入源接错了。**
>
> 稻生自有产线**止于造粒与板材**（鸿波 8/6 确认），主产品是粒料，成型制品是
> 下游入驻企业的事。粒料的质量由 MFR、含水率、灰分、力学性能决定，**镜头看不见**；
> 本项目的头号技术瓶颈（见下方「计算化学」一节）是稻壳纤维与聚合物基体的
> **界面相容性**，表征靠力学测试，镜头同样看不见。
>
> 真实的主数据源是：原料在线检测（近红外水分、粒径分级）+ PLC 工艺点位 +
> 实验室试验机与熔指仪。视觉降级为**板材线的可选项**。
>
> 曾经在 `deck/build-nlzx-v2.js` 里，「视觉质检」出现 4 处而「含水率 / 粒径 /
> MFR / 力学 / 实验室 / 在线检测」出现 0 处 —— 次要数据源列了参与方、留了预算口子，
> 整个价值主张依赖的主数据源一个字没有。改动见 P4 / P6 / P13 / P17。

### 5. 开源模型自部署 + 租赁算力

**租算力 ≠ 用别人的模型服务。** 算力是通用 IaaS，模型自己部署，
推理与向量数据不出自有实例、不经模型服务商。

**向量化比推理侧更关键**：知识库要把全部配方文档做 embedding，
走商业 API 等于最敏感资料一次性全量发给第三方。

**不基于客户数据训练或微调**（8/6 定）。配方与工艺知识以知识库检索的方式使用，
不进模型权重 —— 因为方案自己写死了四条：答案须附出处、配方保密分级、各企业数据隔离、
配方在迭代。权重里的知识说不出来源、没有级别、隔不开、也删不掉，四条一条都满足不了。
样本量也不支持（配方在几百到几千条量级，微调只会过拟合）。
**副作用是好的**：知识产权谈判里「基于谷千禾数据训练所得模型的归属」这个争议高发区直接消失。
正当的微调场景只有一类，且与配方无关 —— 把「抽取动作」固化到轻量抽取层的小模型上。

模型分四层：主力推理 / 向量嵌入 / 视觉理解 / 轻量抽取。
**不预设「开源等于闭源」** —— 须在真实任务上实测选型；
确有不足时可脱敏后调商业 API 兜底，须经数据分级审批，核心配方类不得外发。

### 6. 云优先是 PHASE 1 决策，不是永久架构

现在点位表都没有，服务器与存储按什么规格买无从判断；
而研发数据结构化、认证档案入库不依赖产线，今天就该启动。

```
PHASE 1  云优先（需求未知、快速启动）
PHASE 2  用量摸清后评估：稳定负载可迁本地、弹性负载留云
PHASE 3  按数据分级与总体拥有成本定最终形态
```

**机房选型（自建 vs 托管）结论备查**：纯安全角度专业 IDC 通常优于自建厂区机房，
自建的「安全」多为心理上的；自建不可替代的只有「数据不出厂区」「无第三方接触」两条。
本项目特有物理风险：**稻壳粉碎工序粉尘** · **GPU 功率密度**。

### 7. 治理边界 —— 明确不做什么

- 不做无人干预的自动调参（工艺窗口窄，误调代价不对称）
- **不进产线实时控制回路**（毫秒级与安全联锁归 PLC / DCS）
- 不做质检最终裁决（判定标准解释权在质量部门）
- 不代替人对外承诺（Agent 只出草稿）
- 不做黑箱回答（工艺与合规类须附出处）
- 不承诺无数据支撑的效果

## 七 · 供答客户问，但未上 PPT

### 计算化学（客户 7/28 提出）

**是什么**：用计算机模拟算化学 —— 量子化学计算（DFT）、分子动力学（MD）、
机器学习势。在实验之前先把结果算出来。

**对本项目最有价值的一点：界面相容性。**
天然纤维复合材料的头号瓶颈 —— 稻壳纤维亲水极性、聚合物基体疏水非极性，
结合不牢则力学性能上不去。计算可在合成与试制前筛选偶联剂 / 相容剂候选
（溶解度参数、界面结合能模拟），缩小试错范围。
其次：助剂筛选 · 降解路径 · 食品接触制品的小分子迁移预测。

**局限必须同时说明**：稻壳是天然、变异、非均质的木质纤维素，建模精度有限；
且加工工艺（混炼剪切、热历史）对最终性能的影响往往大于分子层面设计 ——
**现实定位是筛选与缩小范围，不是替代实验。**

**PPT 里的处理**（v29 P7 三处，不单独成页）：
输入列表增列 · 「候选方向建议」任务纳入比对 · 页脚边界注。
口径是：**由高校院所或专业机构承担，不在本方案范围；本方负责结果的结构化入库
与实验/生产数据关联验证** —— 解决「算完了留不下」这个真问题
（请高校做课题，报告交了，数据散在学生电脑里，下次重算）。

## 九 · 内部参考（不进对外方案）

### 能力盘点依据

v29 的 Agent 任务与难度分级基于对既有能力的真实盘点：
工具链 / 技能凝固闭环 / 外部系统接入 / 多模型路由 / 定时触发 / 视觉理解。
**不按宣传口径写。**

### 架构缺口

生产 Agent 的部分场景需要产线边缘节点，而当前是 desktop agent 形态。
7×24 产线场景 + OT/IT 隔离 + 实时性是架构级新增。
**这个缺口在对外方案里体现为 P19 的交付边界（现场零部署，边缘交集成商）——
即：不是能力不足，是边界划分。** 但内部要清楚两者的区别。

### 未决事项

- **商业关系未定**（一次性交付 / 长期运营方 / 合营）—— 决定配套服务说明所有条款的写法，
  也决定「方案里不提我方」是没损失还是隐患
- 临港本地算力资源与支持政策未获取 —— 若有智算中心或补贴，经济账可能改变
- 计算化学的合作方与目标未定
