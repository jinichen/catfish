# 内部 · skill 凝固能力验证计划

> **⚠ 内部文件，不进任何对外材料**（不给稻生、不给投资人）。
>
> 起因：8/6 评估「用鲶鱼改造成完整基座」时，发现整份规划里最乐观的一处修正
> ——把应用层从 309–423 人月砍到 130–210 人月——完全建立在
> 「教学 → 凝固 → 复用」真的成立之上。于是回测了一次存量数据。

---

## 一 · 回测结果（`~/.catfish/`，8/6）

| 指标 | 数值 |
|---|---|
| 教学录制（`recordings/rec_*`） | **6 次**（2026-05 一次，2026-06 五次） |

| 教学凝固且存活的 skill | **0 个** |
| 复用次数 | 无从谈起（没有存活的 skill） |
| 最后一次教学 | 2026-06-23，**距今 43 天** |

---

## 二 · 结论，以及必须同时说明的限定

**不能得出「教学凝固效果不好」这个结论。** 样本有三重局限：

1. 单人开发机的数据，不是生产环境
2. **鸿波本人不是这个功能的目标用户** —— 开发者没有认证申报、工艺调参这类需要凝固的重复业务流程
3. 6 次录制集中在 5–6 月，形态更像功能自测而非真实使用

**能得出的结论是：我们手上没有任何一份真实业务场景下的有效性证据。**

**以及一条必须正视的事实：这个功能 43 天没被任何人用过。**
不是效果问题，是这条产品路径**没有被真实使用打磨过**。而它现在要支撑的，是
daosheng 方案的 AI Native 论证，和一份 3,000–6,000 万规划里的人月假设。

## 三 · 三条验证动作

### 动作一 · 先在我方自己身上用起来（今天就能开始）

找一个内部真实的重复流程教一次。候选：

| 候选流程 | 为什么合适 |
|---|---|
| **mac 包的签名 + 公证 + 装订** | 步骤多、有判断点、这两天刚跑通四轮，记忆最新 |
| daosheng 方案的版本迭代检查 | 有固定检查清单（build → check-geometry → 越界/遮挡/字符扫描） |
| 客户方案的口径一致性核对 | 有明确军规，适合验"规则类知识"能否凝固 |

**这比任何 PoC 都快，而且不占客户资源。**

### 动作二 · 对稻生的口径调整

- ❌ 不说：「平台已具备成熟的能力凝固机制」
- ✅ 改说：「平台提供教学凝固能力，将在阶段一的认证场景上完成首次业务验证」

**把它列为阶段一的验证目标之一，而不是既定前提。**

### 动作三 · 写进阶段一验收标准

认证智能体交付时，同时提交：

- 凝固了几个 skill
- 被复用了几次
- 复用后的人工修改比例
- **★ 是靠配置做出来的，还是最后又写了代码**（附「改了哪些配置、写了多少行代码」清单）

最后一条最容易被糊弄过去 —— PoC 做出来了大家都高兴，没人问是怎么做出来的。
而它直接决定阶段二三的人月弹不弹回去。

## 四 · 判据

| 指标 | 含义 | 达标线（建议，待实测后校准） |
|---|---|---|
| 凝固率 | 演示 N 次 → 成功凝固的比例 | 待定 |
| 存活率 | 凝固后**三个月内仍在被调用**的比例 | ★ 本次回测的存活率是 0，这是最该盯的指标 |
| 复用准确率 | 复用处理新案例的人工核对正确率 | 对齐 P1 方案 M2 的 ≥ 90% |
| 人工修改量 | 每次复用要改多少 | 改一半以上等于没省事 |
| 泛化 | 换市场、换配方还能不能用 | 只能处理演示过的那一例 = 无复用价值 |
| **实现方式** | 配置 vs 写代码 | 直接决定人月假设 |

---

## 五 · 不达标怎么办（先想好，比赌它一定成要稳）

**不是取消项目**，而是：

1. 应用层人月按传统开发弹回去（130–210 → 300 人月量级），预算重报
2. 重新审视 daosheng 方案 P2 那套 AI Native 论证还站不站得住
3. 对稻生的价值主张从「自动凝固」转为「工具链 + 人工建设知识库」——**仍然成立，只是省的人力变少**

第 3 条要提前想清楚：即使凝固机制不理想，方案本身不会垮，但**经济账要重算**。

## 六 · 已知的相邻问题

回测过程中顺带确认的两件事，跟 skill 凝固无关但同属「说好会自动发生、实际没在跑」：

- **定时蒸馏从来没自动跑过**。卡片写着「由 hermes plugin 自动每 24h 跑」，实测
  catfish-memory 没被 hermes 加载，钩子一次都没被调过，
  `.catfish_memory_buffer.jsonl` 停在 7/18。定时器 8/4 才补上。
- **知识库结构指标**（frontmatter 完整率 / 关系类型覆盖 / 引用有效率）以前只有人
  手动跑 `wiki_health.py` 才看得到。8/4 起并进定时器，每 15 分钟一次写进日志。

⚠ **注意**：8/4 那次体检的三个数字（19 个文件缺 frontmatter、408 条边 0 条带类型、
21 组重复）**不能用作「凝固机制不行」的证据** —— 它们反映的是「规则建立之前产生的
存量数据」。类型词表与 frontmatter 要求都是 8/4 才立的。拿存量去证明机制不行是错误
推论，这条我犯过一次，记在这里免得再犯。
